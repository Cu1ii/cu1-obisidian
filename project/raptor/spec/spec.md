# 服务指标上报与分析系统 - 需求规格说明书

> 状态：V1.0（需求定稿）
> 编写日期：2026-04-17
> 适用范围：全量需求（一期 + 二期规划）

---

## 1. 项目目标

搭建一套类似美团 Raptor 的服务指标上报与分析系统，支持多级时间粒度的指标聚合、可视化查询与告警。系统需同时为研发工程师和 SRE 团队提供故障排查与趋势分析能力。

---

## 2. 用户故事

### US-001 作为研发工程师，我希望手动埋点监控任意代码片段

- 我可以标记一段代码的开始和结束，系统自动统计其调用次数和耗时分布
- 我可以在代码片段内嵌套记录事件（如成功、失败、异常类型）
- 我可以在代码片段内记录自定义业务指标，并附带多个标签（tag）用于后续分组分析
- Transaction 支持嵌套，内部使用 traceId + messageId + parentId 维护链路关系：traceId 为链路全局根标识，messageId 为当前节点唯一标识，parentId 为父节点 messageId
- 自研 SDK 服务之间发起 HTTP/RPC 调用时，SDK 通过自研协议 header（`X-RAPTOR-TraceId`、`X-RAPTOR-MessageId`、`X-RAPTOR-ParentId`）传播链路上下文
- 自研 SDK 调用外部 OTel 生态服务时，SDK 将内部 traceId 和当前 messageId 注入 W3C Trace Context（`traceparent` / `tracestate` header）
- 自研 SDK 接收外部 OTel 生态请求时，SDK 从 W3C Trace Context 提取 traceId，生成内部 messageId，恢复链路上下文

### US-002 作为 SRE，我希望查看应用的实时流量与耗时指标

- 我可以看到任意时间范围内的 QPS、总调用量、最大耗时、平均耗时
- 我可以看到 TP90、TP95、TP99、TP999、TP9999 等分位耗时
- 我可以按应用、指标类型、指标名称、自定义标签进行筛选和下钻
- 我可以按机器实例维度拆分指标，排查单机问题

### US-003 作为研发工程师，我希望系统自动采集基础设施指标并手动上报异常

- 系统无需我手动埋点即可自动上报 JVM 指标，指标命名遵循 OpenTelemetry Semantic Conventions（如 `jvm.memory.heap.used`、`jvm.gc.collections.count`）
- 系统无需我手动埋点即可自动上报机器指标（CPU 使用率、内存、磁盘、网络等），指标命名遵循 OpenTelemetry Semantic Conventions（如 `system.cpu.utilization`、`system.memory.usage`）
- 我可以通过 SDK 手动上报异常，支持指定异常类型，系统按类型统计异常数量
- 异常数量支持按时间范围查询，并按异常类型分组展示
- 每个异常类型的链路样本应尽可能上报，用于后续根因定位

### US-004 作为 SRE，我希望在一张图里对比不同时间段的指标趋势

- 我可以选择任意两个时间范围，系统同时展示两条曲线的对比
- 系统支持自动计算日环比、周环比、月环比
- 环比计算基于同一粒度的对应时间窗口

### US-005 作为业务线负责人，我希望自定义业务大盘

- 我可以创建多个大盘面板
- 每个面板可以配置多个指标，并支持简单的四则运算公式（如错误率 = 错误数 / 总数）
- 公式计算支持按标签分组后分别运算（如每个实例的错误率）
- 部分敏感指标面板可以配置为只显示百分比，隐藏绝对数值

### US-006 作为值班 SRE，我希望指标异常时及时收到告警通知

- 我可以配置告警规则，支持静态阈值（如 QPS > 1000）
- 我可以配置环比阈值（如 QPS 较昨日同时段下跌 30%）
- 我可以配置多指标组合规则（如错误率 = 错误数 / 总数 > 5%）
- 告警触发后可以通过飞书或钉钉推送到指定群组或用户

### US-007 作为研发工程师，我希望排查慢请求时能看到调用链路

- 系统可以展示一次请求的完整调用树（Transaction 嵌套 Event），使用 traceId 串联整条链路，使用 messageId + parentId 还原父子关系
- 自研 SDK 服务之间通过自研协议 header（`X-RAPTOR-TraceId`、`X-RAPTOR-MessageId`、`X-RAPTOR-ParentId`）传播链路上下文
- 自研 SDK 与外部 OTel 服务互通时，通过 W3C Trace Context（`traceparent` / `tracestate`）传播链路上下文，traceId 与内部链路共用同一标识
- 链路上报支持抽样，异常请求的抽样比例应高于正常请求
- 针对耗时超过阈值的慢请求，系统应自动或手动触发针对性链路样本上报
- 链路详情页需支持以甘特图形式展示各 Transaction/Event 的耗时分布，直观定位耗时瓶颈
- 链路数据需与指标数据使用同一套埋点 API，避免重复埋点

### US-008 作为平台维护者，我希望系统升级时不丢失核心聚合数据

- 系统支持滚动部署，单节点故障不会导致查询中断
- 系统支持多实例部署，故障切换时有明确的恢复机制
- 核心聚合数据（小时级、天级、周级、月级）在故障场景下不允许丢失

### US-009 作为研发工程师，我希望系统与外部 OpenTelemetry 生态互通

- 自研 SDK 服务之间调用时，通过自研协议 header（`X-RAPTOR-TraceId`、`X-RAPTOR-MessageId`、`X-RAPTOR-ParentId`）传播链路上下文
- 自研 SDK 调用外部 OTel 生态服务时，SDK 将内部 traceId 和当前 messageId 注入 W3C Trace Context（`traceparent` / `tracestate` header）
- 自研 SDK 接收外部 OTel 生态请求时，SDK 从 W3C Trace Context 提取 traceId，生成内部 messageId，恢复链路上下文
- traceId 作为链路全局根标识，内部链路树和外部 OTel 链路共用同一 traceId；messageId 作为内部节点标识，parentId 用于还原父子关系

## 3. 验收标准

### 3.1 指标类型与覆盖范围

| 指标大类 | 包含内容 | 验收标准 |
|---------|---------|---------|
| Transaction | 任意代码片段的调用次数、耗时分布 | 支持嵌套，一个 Transaction 内可以创建多个子 Transaction；子 Transaction 通过 parentId 关联父 Transaction；嵌套层级不做硬性限制，但建议不超过 64 层以避免栈溢出和查询性能问题 |
| Event | 无耗时事件计数，可携带状态 | 支持挂载到 Transaction，支持独立上报 |
| Business/Metric | 自定义计数、耗时指标，支持多维度 tag | tag 的笛卡尔积组合数上限 1000 |
| Hosts/Heartbeat | JVM 指标、机器指标（CPU/内存/磁盘/网络） | 自动采集，无需业务代码埋点 |
| Problem | 应用异常数量统计 | 手动上报，支持指定异常类型；按类型分组统计；支持时间范围查询；每个类型的异常链路样本尽可能上报 |
| OTel 兼容 | 对外链路传播兼容 | SDK 注入/解析 W3C Trace Context（`traceparent` / `tracestate`）；内部保留 messageId 体系；外部互通时额外生成 W3C traceId/spanId；Hosts 指标命名遵循 OTel Semantic Conventions |

### 3.2 时间粒度与查询

| 粒度 | 支持情况 | 查询延迟要求 |
|------|---------|-------------|
| 秒级 | 支持 | 数据上报到可查询 <= 15 秒 |
| 分钟级 | 支持 | 查询延迟 < 500ms |
| 小时级 | 支持 | 查询延迟 < 500ms |
| 天级 | 支持 | 查询延迟 < 2s |
| 周级 | 支持 | 查询延迟 < 2s |
| 月级 | 支持 | 查询延迟 < 2s |
| 自定义范围 | 支持任意两个时间点 | 自动选择最优底层粒度 |

### 3.3 环比能力

- 系统支持日环比、周环比、月环比的自动计算
- 系统支持用户手动选择任意两个时间范围进行对比
- 环比计算基于相同粒度（如都用分钟级或都用小时级），避免粒度不一致导致的偏差

### 3.4 分位数精度要求

分位数通过直方图（Histogram）方式计算，误差要求如下：

| 耗时范围 | 允许最大相对误差 |
|---------|-----------------|
| 0 ~ 500ms | < 1% |
| 500 ~ 1000ms | < 10% |
| 1000 ~ 3000ms | < 15% |
| > 3000ms | 不做严格要求 |

### 3.5 数据保留策略

| 数据粒度 | 保留时长 |
|---------|---------|
| 秒级/分钟级 | >= 半年 |
| 天级/周级 | >= 1 年 |
| 月级 | 永久 |

### 3.6 SDK 性能要求

| 指标 | 要求 |
|------|------|
| 埋点耗时 | 毫秒级（单次埋点 < 1ms） |
| CPU 开销 | 尽可能控制在 1% - 5% |
| 失败影响 | 上报失败不得阻塞业务主线程，不得抛异常 |

### 3.7 高可用要求

- 一期：支持多实例部署，按指标分区哈希路由，主备切换时允许丢失一个可配置快照周期内的数据（默认建议 5 ~ 10 秒）
- 核心聚合数据（小时级及以上）在故障恢复后必须保证最终一致性，不允许长期丢失
- 二期：增强为外部状态存储方案，实现 Collector 无状态化

### 3.8 告警要求

- 支持静态阈值告警
- 支持环比阈值告警
- 支持多指标组合公式告警
- 告警触发条件支持以下两种模式，可配置：
  - **打点计数模式**：N 分钟内至少出现 M 个满足告警条件的打点即触发
  - **触发次数模式**：N 分钟内告警条件被触发至少 M 次即触发
- 告警通知渠道至少支持飞书和钉钉

### 3.9 可视化要求

- 支持 PC 浏览器访问，移动端兼容作为加分项
- 支持按 app-key、指标类型、指标名称、自定义 tag、实例维度进行筛选和分组
- 支持大盘自定义和简单公式计算
- 支持部分指标的数值脱敏（只显示百分比，隐藏绝对数量）

### 3.10 多语言支持

- 一期优先支持 Java SDK
- 后续需支持 Go、Python、Node.js 接入
- 各语言 SDK 的埋点 API 风格保持一致

### 3.11 OTel 兼容要求

- 自研 SDK 服务之间调用时，通过自研协议 header（`X-RAPTOR-TraceId`、`X-RAPTOR-MessageId`、`X-RAPTOR-ParentId`）传播链路上下文
- 自研 SDK 调用外部 OTel 生态服务时，自动注入 W3C Trace Context（`traceparent` / `tracestate` header），格式遵循 W3C 标准；traceId 与内部链路共用同一标识，spanId 使用当前 messageId 填充
- 自研 SDK 接收外部 OTel 生态请求时，自动解析 W3C Trace Context 提取 traceId，生成内部 messageId，恢复链路上下文
- 内部 Transaction 使用 traceId + messageId + parentId 三元组：traceId 为链路全局根标识，messageId 为当前节点唯一标识，parentId 为父节点 messageId
- Hosts 指标（JVM、机器指标）的命名遵循 OpenTelemetry Semantic Conventions
- 一期暂不要求 Collector 接收 OTLP 数据，但架构上预留 OTLP Receiver 扩展点，作为二期能力

## 4. 边界情况

### 4.1 链路传播协议选择

- 自研 SDK 服务之间调用时，使用自研协议 header（`X-RAPTOR-TraceId`、`X-RAPTOR-MessageId`、`X-RAPTOR-ParentId`）传播链路上下文
- 自研 SDK 调用外部 OTel 生态服务时，将内部 traceId 和当前 messageId 注入 W3C Trace Context（`traceparent` / `tracestate` header）
- 自研 SDK 接收外部请求时，若 `traceparent` header 格式不合法（如版本号不支持、字段长度不对、非法字符），应丢弃该 header，视为无上游链路上下文，不影响当前请求处理
- 自研 SDK 调用外部 OTel 服务时，若 traceId 生成或 W3C 编码失败，应降级为仅携带自研协议的上下文 header，保证内部链路不断
- W3C `tracestate` header 长度超过 512 字符时，允许截断或丢弃，避免 header 过大影响网关/代理
- 自研服务作为链路入口（无上游链路上下文）时，SDK 需同时生成新的 traceId（W3C 格式）和新的 messageId，两者从同一源头生成，保证唯一性和一致性

### 4.2 Transaction 嵌套边界

- Transaction 支持嵌套，一个父 Transaction 内可以创建多个子 Transaction，子 Transaction 通过 parentId 关联父 Transaction 的 messageId
- 嵌套层级不设硬性上限，但 SDK 和 Collector 需具备循环引用检测能力，若发现 parentId 与 messageId 形成循环依赖（如 A 的 parentId 指向 B，B 的 parentId 又指向 A），应截断循环并记录异常日志
- 过深嵌套（如超过 64 层）可能导致链路查询性能下降，SDK 侧建议配置最大嵌套深度软限制，超限后以打日志或采样方式告警，但不阻断业务执行
- 子 Transaction 的耗时不计入父 Transaction 的耗时（父子耗时独立统计），父 Transaction 的总耗时是其自身代码段的 wall-clock 时间，而非各子 Transaction 耗时的简单加和

### 4.3 标签基数爆炸

- Business 指标支持用户自定义 tag，但 tag 的笛卡尔积组合数必须限制在 1000 以内
- 超出限制时，系统将超出的组合自动归并到一个名为 `others` 的统一标签值中，避免存储和查询性能崩溃

### 4.4 低流量场景下的分位数

- 当某时间窗口内请求量极低（如每秒 < 10 条）时，TP9999 会趋近于最大值，分位数失去统计意义
- 系统应在查询结果中标注数据可信度（如"样本量不足，分位数仅供参考"），或支持设置最小样本量阈值

### 4.5 跨粒度查询边界

- 当用户查询的自定义时间范围跨越多个数据粒度时（如前 6 小时用分钟级，后 18 小时用小时级），系统需在边界处保证数据连续性和一致性
- 跨粒度拼接时不允许出现数据重复或断崖式跳变

### 4.6 Collector 故障切换

- 主 Collector 故障后，SDK 应在可接受时间内（建议 < 5 秒）切换到备用 Collector
- 切换期间的数据可选择丢弃（优先保证实时性）或本地缓冲（优先保证完整性），该策略需可配置
- 故障恢复后，系统不应出现数据重复计算

### 4.7 超长耗时

- 超过直方图最大桶边界（如 3000ms 以上）的耗时统一归入 +Inf 桶
- 在展示 Max 耗时和 TP 分位数时，系统需明确说明 +Inf 桶的存在及其对精度的影响

### 4.8 历史数据补录

- 若因网络或 Collector 故障导致某段时间数据缺失，系统不支持事后补录原始明细数据
- 已聚合的分钟级/小时级数据一旦落盘，不允许修改

### 4.9 公式计算除零

- 大盘公式计算中若出现除数为零的情况（如错误率 = 错误数 / 总数，总数为 0），系统应返回空值或特定占位符（如 "N/A"），不得抛出异常或显示无穷大

### 4.10 告警风暴

- 当大量指标同时触发告警时，系统应具备基本的告警收敛或去重机制，避免短时间内向同一渠道推送重复通知

### 4.11 多实例数据查询与合并

- 同一应用部署在多个实例上时，聚合后的 QPS 应为各实例之和，平均耗时应为加权平均（按请求量加权），TP 分位数应基于全局直方图合并后计算
- 不允许简单地对各实例的 TP99 取平均值作为全局 TP99
- 系统支持用户选择单个或多个实例进行独立查询，也支持对选中的若干实例做聚合查询
- 实例筛选需支持按实例名称或标识进行精确匹配和批量选择

### 4.12 自定义时间范围过大

- 当用户选择的自定义时间范围过大（如查询过去 3 年的秒级数据）时，系统应拒绝查询或自动降级到合适的粒度，并给出明确提示
- 查询返回的数据点数量应设置上限（如最多 10000 个点），超出时提示用户缩小范围或降低粒度

## 5. 待决策项（不影响本期 spec 定稿）

以下问题在需求层面已明确方向，但具体实现方案需在技术设计阶段进一步细化：

1. **Trace 存储与查询**：链路追踪的数据量和存储形态与指标完全不同，一期埋点数据结构需为 Trace 预留扩展，但 Trace 的独立存储和查询 UI 可放在二期
2. **告警引擎选型**：使用开源告警组件快速落地，还是自研告警规则引擎以支持更灵活的环比和多指标组合
3. **长期存储引擎**：月级永久保留的数据量极大，Prometheus 单机 TSDB 可能无法承载，需评估是否需要引入长期存储（如对象存储 + 降采样查询引擎）
