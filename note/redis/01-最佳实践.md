Squirrel 实在 RedisCluster 之上构建的高可用缓存存储, 由于底层使用的是 Redis, 所以在使用 Squirrel 的时候应该根据 Redis 本身的特性扬长避短, 充分发挥 Redis 的性能优势

# 最佳场景 -- 小容量, 热数据

由于 Squirrel 使用的是存内存存储, 提供的是更高的性能以及更好可用性的缓存系统. 所以, 从成本, 资源利用率一级缓存系统特性来说, Squirrel 更加适合存储一写热数据 -- 即经常被访问的数据可以存储在 Squirrel 中. 希望的是 Squirrel 中的绝大部分数据一天内是会被全部访问到的, 对于大量的超过几天时间都不会被访问的数据存储在 Squirrel 里面则比较浪费

# 最佳实践与需要注意的坑

## 选择合适的数据结构

Redis 原生支持的 string, hash, set, sortedSet, list 等数据结构以及支持复杂的场景需求

## 杜绝 BigKey, HotKey

- 比如 string 类型的 value 超过 1 MB, hash, set, zset, list 这些集合类型的元素超过 1 W 个, 推荐 [大 value 的拆分参考](./02-大%20Value%20分拆,%20多%20key%20合并方案.md)
- HotKey 容易造成 CPU, 网络上的高负载, 建议业务对热点 key 有降级方案

## 单集群 Key 个数 < 1 亿

key 个数过多会消耗大量的额外内存 [多 key 的合并方式参考](02-大%20Value%20分拆,%20多%20key%20合并方案.md)

## 主动更新缓存

被动更新缓存可能会给 DB 带来压力, 推荐可以通过订阅数据库的变更或者其他方式来更新缓存中的 key

## 关注集群内存

内存在满载情况会对业务有明显的性能影响, 建议在集群内存占用较高的时候尝试优化, 或者联系 DBA 进行扩容操作

## 设置合理的过期时间

key 的过期时间应该尽量的短, 减少内存占用; 避免出现大量 key 同时过期的情况

## 使用 multiGet 或者 pipeline 提速

使用 multiGet 或者 pipeline 能够讲多次的缓存操作合并到一次网络请求中, 大大减少网络开销.

## 避免复杂操作

- multi 以及 pipeline 等批量操作中的 key 个数不要太多, 避免复杂度为 O(N) 的集合类操作, 比如 Hgetall
- multi, pipeline, hgetall 如何选择? 如果 key 本身不超过 100, 建议存放在 hash 中, hash 批量获取可以减少网络 IO (只获取一个 key 和获取多个 key 的区别)

## 不要过度使用

比如不要使用 list 去做消息队列, Redis 不保证这些功能的可靠性. 有这类需求的可以去使用架构的其他组件, 专业的事由专业的组件来做.

# 推荐容灾方案

大部分场景下, 推荐业务使用双机房部署方案, 一个机房部署主节点, 一个机房部署从节点, 可以满足绝大多数的场景需求. 极端场景下可能主节点所在的机房掉电, 那么集群处于不可用状态 (此时可以通过人工介入来恢复集群的可用状态)

对可用性要求高的业务推荐使用三机房部署方案, 即使在一个机房掉电的场景下也可以保证集群的高可用
