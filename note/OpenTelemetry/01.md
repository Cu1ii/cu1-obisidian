# 01 · OpenTelemetry 是什么：三类 Signal 与数据模型

> 前置知识：分布式系统基本概念（服务、RPC/HTTP 调用）、知道什么是日志和监控指标
> 难度：入门
> 预计阅读时间：15 分钟

## 正文内容

### 1. 为什么先学"概念"而不是先 `pom.xml`

很多人学 OpenTelemetry（下称 **OTel**）一上来就抄一段 Java Agent 启动命令，跑通后看到 Jaeger 里有彩色的瀑布图就以为"会了"。这是典型的**只学了工具，没学数据模型**。等到生产环境出现 trace 断裂、采样率失控、标签爆基数（high cardinality）时，没人能回答"这条数据从哪来、到哪去、为什么丢了"。

所以我们从最底层开始：OTel **本质上是一套可观测性数据的标准**，而不是某个具体工具。它定义了三件事：

1. **数据长什么样**（数据模型 / Specification）
2. **怎么产生这些数据**（API + SDK）
3. **怎么传输这些数据**（OTLP 协议 + Collector）

把这三件事吃透，剩下的 Java / Go / Collector 配置都是顺水推舟。

---

### 2. 三类 Signal：Traces / Metrics / Logs

可观测性（Observability）三大支柱，OTel 把它们统一在一个项目里。三者**不是替代关系，而是回答不同问题**：

| Signal | 数据形态 | 回答的问题 | 典型例子 |
|--------|---------|----------|---------|
| **Traces** | 带因果关系的事件链 | "这一次请求**为什么**慢/失败？经过了哪些服务？" | 一次下单请求穿过 7 个微服务的调用链 |
| **Metrics** | 按时间聚合的数值 | "**整体趋势**怎样？是否超出阈值？" | QPS、P99 延迟、错误率、CPU |
| **Logs** | 离散的、带时间戳的文本/结构化事件 | "**具体**这一刻发生了什么？" | "用户 123 登录失败：密码错误" |

> ⚠️ **关键直觉**：Trace 是"一次请求的剖面"，Metric 是"一段时间的切面"，Log 是"一个时间点的快照"。
> Trace 帮你定位**哪条请求出问题**，Metric 帮你**发现有问题**，Log 帮你**看清那一刻细节**。

举个具体例子：用户反馈"昨天 10 点下单偶尔失败"。

- **Metric** 告诉你：10 点订单服务错误率从 0.1% 飙到 5%。 → 发现问题。
- **Trace** 告诉你：失败请求都卡在了 inventory 服务的某个 DB 查询。 → 定位问题。
- **Log** 告诉你：那个查询打出了 `connection pool exhausted`。 → 看清问题。

这三类数据**单独都能用**，但 OTel 的野心是把它们用统一的 **Context（上下文）** 串起来——一条 Log 里能带上当前的 trace_id，一条 Metric 能带上 exemplar 指向具体的 Trace，最终形成"一键跳转"的体验。

### 3. Trace / Span / Context：分布式追踪的最小数据模型

Trace 是 OTel 里最重要也最容易讲偏的概念。先记三个原子单位：

> **Trace** = 一次端到端请求的完整记录，由若干 **Span** 组成的一棵树。
> **Span** = 一次"有边界的操作"，比如一次 HTTP 调用、一次 DB 查询、一段业务逻辑。
> **Context** = 在进程内/进程间传递的"我现在属于哪个 Trace 的哪个 Span"信息。

**每个 Span 必带的字段**（精简版）：

```
trace_id        : 整个 Trace 全局唯一（128 位）
span_id         : 当前 Span 唯一（64 位）
parent_span_id  : 父 Span 的 span_id；根 Span 此字段为空
name            : 操作名，如 "GET /api/orders"
start_time / end_time
attributes      : 键值对，如 http.method=GET, db.system=mysql
events          : Span 生命期内的有序事件（带时间戳的小日志）
status          : OK / ERROR / UNSET
```

举个例子，用户发起 `GET /order/123`：

```
[A] gateway: GET /order/123                trace_id=T1, span=A, parent=∅
 └─[B] order-svc: getOrder(123)             trace_id=T1, span=B, parent=A
     ├─[C] order-svc: SELECT FROM orders    trace_id=T1, span=C, parent=B
     └─[D] inventory-svc: checkStock(...)   trace_id=T1, span=D, parent=B
         └─[E] inventory-svc: SELECT ...    trace_id=T1, span=E, parent=D
```

整棵树 5 个 Span，**共享同一个 `trace_id`**，靠 `parent_span_id` 串起父子关系。注意 **B 和 D 不在同一个进程**——gateway 调 order-svc 是一次跨进程的 RPC——所以 Span B 的 `trace_id` + `span_id` 必须通过网络（HTTP header）传给 inventory-svc，这就是**Context Propagation**。

---

### 4. Context Propagation 与 W3C TraceContext

OTel 默认的传播协议是 **W3C TraceContext**（一个 W3C 标准，独立于 OTel 存在）。它在 HTTP 请求里加一个 header：

```
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
             │  │                                │                │
             │  trace-id (16 字节, 32 hex)        │                │
             version                              parent-id (8 字节) trace-flags (采样标志等)
```

接收方解析这个 header，就知道：
- 这次请求属于 trace_id = `4bf92f3577...4736`
- 它的父 Span 是 `00f067aa0ba902b7`
- 采样位是 01（被采样）

接收方在本地创建新 Span 时，新 Span 的 `parent_span_id` 就填这个 `00f067aa...`，整棵树就连上了。

**Baggage** 是它的兄弟（也是 W3C 标准），用同样的方式传播业务键值对，比如 `baggage: user_id=42,tenant=acme`。**Baggage 不是 Span 的 Attribute**，它是跨服务的"行李箱"，下游任何服务都能读取并加到自己的 Span 上。

> ⚠️ 易混点：trace_id 不是你的业务 ID，也不是某个具体 Span。它只是"这棵树的标识符"。一棵 Trace 树可以有几十个 Span 共享同一个 trace_id。

### 5. OTel 架构：API / SDK / Collector / Exporter

理解了数据，再看产生与传输的链路。OTel **故意把"产生数据"和"发送数据"彻底拆开**：

```
应用代码
  ↓ 调用
[OTel API]   ← 只定义接口，不做事；可零成本接入
  ↓ 在运行时绑定到
[OTel SDK]   ← 真正实现：采样、批处理、序列化
  ↓ 通过
[Exporter]   ← 把数据序列化为 OTLP / Jaeger / Zipkin 等格式
  ↓ 发送给
[OTel Collector]（可选但强烈推荐）
  ↓ 再 fan-out 给
后端（Jaeger / Tempo / Prometheus / Loki / Datadog / ...）
```

**API 与 SDK 为什么必须分离**：库作者（如某个 HTTP client 库）只想"打 Span"，不应该关心"用什么后端、什么采样率"。所以库依赖 API（轻量、稳定），应用依赖 SDK（重型、配置化）。一个没引入 SDK 的应用，所有 API 调用都是 no-op，零开销。这是个非常关键的设计，决定了 OTel 能被广泛集成。

**Collector** 是个独立进程，作用是：
- 把多种来源（OTLP、Jaeger、Prometheus scrape）汇聚
- 中间做处理（采样、过滤、加属性、脱敏）
- 再分发给多个后端

应用通常**只配置一个 exporter 指向本地 Collector**，至于数据怎么转发到 Jaeger / Datadog / Tempo，由 Collector 集中决定。这样换后端不用改应用代码。

### 6. 一张图收尾

```
┌────────────┐   API 调用     ┌────────────┐
│  你的应用   │ ─────────────→ │  OTel SDK  │
│ (Java/Go)  │                │  采样+批处理 │
└────────────┘                └─────┬──────┘
                                    │ OTLP/gRPC
                                    ↓
                              ┌──────────────┐
                              │ OTel Collector│
                              │ recv/proc/exp │
                              └──┬─────┬─────┘
                                 ↓     ↓
                              Jaeger Prometheus
                              (Traces) (Metrics)
```

把这张图刻进脑子，后面学 Java/Go SDK 时所有 API 都能对号入座。

1. 你的服务遇到"用户登录失败"问题。分别用 **Log / Metric / Trace** 能回答哪些不同的问题？反过来，三者都缺哪一类时，最难定位的是哪种故障？

3. 假设你写了一个 HTTP client 通用库，希望它"默认产出 Span，但不强制使用者引入某个具体后端"。OTel 的 **API/SDK 分离**设计是怎么帮你做到的？如果没有这个设计，会出什么问题？
