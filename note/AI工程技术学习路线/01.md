# 先把地图画对：AI 工程到底学什么

> 前置知识：会写基础代码；知道 API、服务、前后端或脚本自动化中任意一种即可。
> 难度：入门
> 预计阅读时间：15 分钟

## 正文内容

学习 AI 工程，最容易踩的坑不是「学得慢」，而是**把不同岗位、不同层级的知识混成一团**。

有人一上来啃 Transformer 论文，以为不懂注意力机制就不能做 AI 应用；有人只学提示词，以为会写 Prompt 就等于会做 AI 工程；有人追着每个新模型跑，结果一个完整产品都交付不出来。

先立一个核心判断：

> **AI 工程不是「研究模型为什么聪明」，而是「把不稳定的智能能力，接进稳定的软件系统」。**

这句话里有两个关键词：

- **不稳定的智能能力**：大模型输出会变；同一个问题可能给不同答案；它可能幻觉、遗漏、误解上下文。
- **稳定的软件系统**：用户需要可靠功能；公司需要成本可控；系统需要权限、安全、日志、评估和迭代。

AI 工程师站在这两者中间。

---

## 一、先分清四类 AI 技术工作

### 1. AI 研究

AI 研究关注：**模型能力边界如何被推进**。

典型问题：

- 新结构能不能提升推理能力？
- 训练目标怎么设计？
- 模型为什么会出现某种行为？

这类工作更接近论文、数学、实验和模型机制研究。

如果目标是做 AI 应用工程，不需要一开始就深挖这里。知道大概原理有帮助，但不是第一优先级。

### 2. 模型训练 / 微调工程

模型训练关注：**如何让模型在特定数据和任务上表现更好**。

典型问题：

- 数据集怎么清洗？
- 怎么做监督微调或偏好优化？
- 训练成本、显存、吞吐怎么控制？

这条线很重要，但门槛更高，也更依赖数据和算力。

多数 AI 应用团队不会从训练模型开始，而是先用现成模型验证产品闭环。

### 3. AI 应用工程

AI 应用工程关注：**如何把模型能力变成功能**。

典型问题：

- 用户问题怎么转成模型可用上下文？
- 模型什么时候该调用工具？
- 怎么接数据库、搜索、文件、代码执行器？
- 输出错了怎么评估？
- 成本高了怎么降？
- 权限和安全怎么控？

这就是本课题主线。

你学 AI 工程，最先该抓住这条线。

### 4. AI 平台工程

AI 平台工程关注：**如何让多个 AI 应用稳定、高效、可观测地运行**。

典型问题：

- 模型网关怎么做？
- 多模型路由怎么做？
- Prompt、评估集、调用日志怎么管理？
- Agent 工具权限怎么隔离？
- 服务怎么部署、监控、灰度？

它比应用工程更底层、更偏基础设施。等你做过几个 AI 应用后，再学平台工程会更自然。

## 二、用五段式框架看任何 AI 工程系统

先别急着学 LangChain、RAG、Agent、微调。先学一个更稳定的观察框架：

> **输入 → 模型 → 工具 → 评估 → 交付**

几乎任何 AI 应用，都可以放进这个框架里。

### 1. 输入：用户到底给了什么

输入不只是用户打的一句话。

它可能包括：

- 用户问题
- 当前页面内容
- 历史对话
- 用户权限
- 业务数据
- 文件、图片、代码、日志
- 系统约束和输出格式

AI 工程第一步，是把这些材料整理成模型能用的**上下文**。

很多 AI 应用效果差，不是模型差，而是上下文构造差：该给的信息没给，不该给的信息塞太多，关键约束放在模型容易忽略的位置。

### 2. 模型：选择哪个智能核心

模型负责生成、分类、抽取、推理、规划或改写。

工程上要问的问题不是「哪个模型最强」，而是：

- 这个任务需要多强推理？
- 延迟能接受多少？
- 成本上限是多少？
- 输出稳定性要求多高？
- 是否需要长上下文、多模态、工具调用？

模型选择是工程权衡，不是排行榜崇拜。

### 3. 工具：模型不能只靠嘴

很多真实任务不能只靠模型回答。

例如：

- 查订单：需要数据库或 API。
- 写代码：需要读文件、改文件、跑测试。
- 分析知识库：需要检索文档。
- 订会议：需要日历工具。

工具让模型从「会说」变成「能做」。

但工具也带来风险：权限越权、误操作、注入攻击、结果不可控。所以 AI 工程不是「给模型更多工具就更强」，而是设计**工具边界**。

### 4. 评估：怎么知道它做对了

传统软件常靠单元测试判断对错；AI 系统更麻烦，因为输出常是自然语言，不只有一个标准答案。

所以要设计多层评估：

- 离线评估：固定题集，看版本变化是否变好。
- 人工评估：让人判断答案是否有用、准确、安全。
- 在线指标：看用户采纳率、重试率、投诉率、延迟、成本。
- 失败样本回流：把错例变成下一轮改进材料。

没有评估，AI 应用会变成玄学调参。

### 5. 交付：用户真正用到什么

交付不是把模型接上 API 就结束。

还要考虑：

- 用户界面怎么承接不确定输出？
- 出错时是否能解释和恢复？
- 延迟高时怎么提示？
- 成本超预算时怎么降级？
- 敏感操作是否需要确认？
- 日志是否能复盘一次失败调用？

AI 工程的成熟度，往往体现在这些「模型之外」的地方。

## 三、学习路线先不要按工具排，要按能力排

很多人会这样列路线：Python → Prompt → LangChain → RAG → Agent → 微调 → 部署。

这不算错，但容易变成工具清单。

更好的路线是按能力排：

1. **会定义任务**：判断一个 AI 功能到底要解决什么问题。
2. **会构造上下文**：知道给模型什么、不该给什么、怎么组织。
3. **会调用模型**：懂参数、流式输出、结构化输出、错误处理。
4. **会接工具和数据**：让模型查资料、调用 API、执行动作。
5. **会做评估**：用样本和指标判断效果，而不是凭感觉。
6. **会工程化交付**：处理成本、延迟、安全、权限、监控和迭代。

工具会变，但这些能力迁移得更久。

## 四、你现在该怎么判断优先级

用三个问题判断：

### 问题 1：你能不能独立写一个普通软件功能？

如果不能，先补基础工程能力：

- Python 或 TypeScript 基础
- HTTP API
- JSON
- 数据库基本读写
- Git
- 基础测试

**注释：**「这些基础我都有」

AI 应用本质仍是软件。不会普通工程，AI 部分会放大混乱。

### 问题 2：你能不能解释一次模型调用从输入到输出发生了什么？

如果不能，先补模型调用基础：

- Message 结构
- System / user / assistant 角色
- Token 和上下文窗口
- Temperature 等生成参数
- 流式输出
- 结构化输出
- 工具调用

**注释：** 这里我解释不出来

不需要先懂训练细节，但要懂调用接口如何影响行为。

### 问题 3：你能不能让一个 AI 功能稳定复现效果？

如果不能，优先学评估和工程化：

- 固定测试样本
- Prompt 版本管理
- 输出格式校验
- 错误重试
- 失败样本记录
- 成本和延迟统计

这一步区分「玩 Demo」和「做工程」。
