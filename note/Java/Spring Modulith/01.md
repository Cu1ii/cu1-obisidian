# Spring Modulith：先把单体应用切成可验证的业务模块

> 前置知识：Spring Boot 分包、依赖注入、JUnit 基础、事务基础
> 难度：入门
> 预计阅读时间：15 分钟

## 正文内容

如果你想基于 Spring Modulith 重构现有项目，第一步不是加框架注解，也不是拆服务，而是回答一个更底层的问题：

> 这个 Spring Boot 应用内部，到底有哪些**业务模块**？每个模块允许别人用什么？禁止别人碰什么？

很多单体应用变复杂，不是因为「单体」天然差，而是因为内部边界消失了：

- `order` 直接调 `inventory.internal`；
- `user` 随手注入 `payment` 的实现类；
- 某个 `common` 包越来越大，最后变成所有模块的暗门；
- 改一个功能时，不知道会影响哪些业务能力。

Spring Modulith 的核心价值是：**在一个 Spring Boot 单体应用里，把模块边界显式建模、自动验证、可视化，并支持模块间通过事件解耦。**

它不是微服务框架。它更像一个「模块治理工具箱」：你仍然部署一个应用，但代码结构、依赖方向、测试粒度、模块协作方式开始变得可控。

官方参考文档明确提到，Spring Modulith 支持开发者在 Spring Boot 应用中实现逻辑模块，并提供结构验证、模块文档、单模块集成测试、运行期模块交互观察，以及松耦合模块交互能力。

---

## 1. Spring Modulith 的几个核心特性

### 1.1 应用模块建模：从包结构推导模块

Spring Modulith 默认从 Spring Boot 主类所在包下面分析子包，并推导出应用模块模型。

典型结构：

```text
com.example.shop
├── ShopApplication.java
├── order
│   ├── OrderManagement.java
│   └── internal
│       └── OrderValidator.java
├── inventory
│   ├── InventoryManagement.java
│   └── internal
│       └── StockCalculator.java
└── payment
    ├── PaymentManagement.java
    └── internal
        └── PaymentGatewayAdapter.java
```

在这个结构里，`order`、`inventory`、`payment` 通常会被识别为三个应用模块。

默认规则可以先粗略记成：

- 模块根包是模块 API；
- 模块根包下面的 `internal` 等子包属于模块内部实现；
- 其他模块不应该依赖某个模块的内部实现；
- 模块之间的依赖关系可以被 Spring Modulith 验证出来。

这点非常适合重构老项目：你可以先不改业务逻辑，只让框架帮你画出现有依赖关系，然后看哪里已经越界。

---

### 1.2 结构验证：让模块边界变成测试

最小用法是写一个 JUnit 测试：

```java
import org.junit.jupiter.api.Test;
import org.springframework.modulith.core.ApplicationModules;

class ModularityTests {

    @Test
    void verifiesModularStructure() {
        ApplicationModules modules = ApplicationModules.of(ShopApplication.class);
        modules.verify();
    }
}
```

这个测试做两件事：

1. 基于 `ShopApplication` 所在包扫描模块结构；
2. 校验模块之间是否出现非法依赖。

一旦项目里有类似 `order` 依赖 `inventory.internal.StockCalculator` 这样的越界访问，测试就会失败。

这就是 Spring Modulith 很适合「重构前探测」的原因：

> 你不需要先凭感觉说项目乱在哪里，而是先让 `ApplicationModules.of(...).verify()` 把真实依赖问题暴露出来。

---

### 1.3 显式依赖声明：模块只能依赖被允许的模块

当你希望某个模块只能依赖指定模块，可以在模块根包增加 `package-info.java`：

```java
@org.springframework.modulith.ApplicationModule(
    allowedDependencies = "inventory"
)
package com.example.shop.order;
```

含义：`order` 模块只允许依赖 `inventory` 模块，以及不属于任何模块的代码。

这适合用在重构中后期：

- 前期先扫描真实依赖，不急着加约束；
- 中期确定目标架构后，为核心模块加 `allowedDependencies`；
- 后期让 CI 跑 `modules.verify()`，防止新代码重新破坏边界。

---

### 1.4 命名接口：允许别人依赖一小块 SPI，而不是整个内部包

有时模块不只暴露根包 API，还需要暴露某个特定接口包，比如：

```text
order
├── OrderManagement.java
├── spi
│   └── OrderCompletedHandler.java
└── internal
    └── OrderInternalService.java
```

可以在 `order.spi` 下加：

```java
@org.springframework.modulith.NamedInterface("spi")
package com.example.shop.order.spi;
```

这样其他模块可以依赖 `order::spi` 这个命名接口，而不是依赖 `order.internal`。

直觉上，它解决的是这个问题：

> 我不是要打开整个模块，我只是要打开一个可控的门。

---

### 1.5 模块事件：用业务事件降低模块耦合

模块之间并非只能直接调用。Spring Modulith 鼓励用 Spring 应用事件表达跨模块协作。

比如订单完成后，库存模块需要扣减库存：

```java
public record OrderCompleted(Long orderId) {}
```

订单模块发布事件：

```java
@Component
class OrderManagement {

    private final ApplicationEventPublisher events;

    OrderManagement(ApplicationEventPublisher events) {
        this.events = events;
    }

    void completeOrder(Long orderId) {
        // 订单完成逻辑
        events.publishEvent(new OrderCompleted(orderId));
    }
}
```

库存模块监听事件：

```java
@Component
class InventoryManagement {

    @ApplicationModuleListener
    void on(OrderCompleted event) {
        // 扣减库存
    }
}
```

官方文档说明，`@ApplicationModuleListener` 是一种便捷注解，用来表达模块间基于事件集成的默认方式。它相当于把常见的异步、事务事件监听模式封装成更清晰的模块监听器。

什么时候适合用事件？

- 一个模块完成业务动作后，其他模块需要「知道这件事」；
- 发布方不应该关心有几个订阅方；
- 订阅方失败不应该反向污染发布方代码；
- 你希望未来有机会把某些模块拆出去。

什么时候不必用事件？

- 强一致、同步返回结果的查询；
- 简单的模块内调用；
- 事件只是在隐藏糟糕的依赖关系。

---

### 1.6 模块测试：只启动一个模块做集成测试

Spring Modulith 提供 `@ApplicationModuleTest`：

```java
import org.springframework.modulith.test.ApplicationModuleTest;

@ApplicationModuleTest
class OrderIntegrationTests {

    // 测试 order 模块
}
```

它类似 `@SpringBootTest`，但启动范围限制在当前应用模块。这样可以降低集成测试成本，并让你发现模块是否真的能独立启动。

如果模块通过事件协作，还可以用 `PublishedEvents` 验证某个操作是否发布了预期事件：

```java
@ApplicationModuleTest
class OrderIntegrationTests {

    @Test
    void publishesOrderCompleted(PublishedEvents events) {
        // 执行业务操作

        var matching = events.ofType(OrderCompleted.class);

        assertThat(matching).hasSize(1);
    }
}
```

更复杂的异步场景，可以用官方提供的 `Scenario` API 编写模块集成测试。

---

### 1.7 文档化：生成模块关系图和模块画布

Spring Modulith 的 `Documenter` 可以基于 `ApplicationModules` 生成文档片段，包括：

- C4 / UML 组件图；
- Application Module Canvas；
- 模块中的 Spring Bean、聚合根、发布事件、监听事件、配置属性等信息。

示例：

```java
class DocumentationTests {

    ApplicationModules modules = ApplicationModules.of(ShopApplication.class);

    @Test
    void writeDocumentationSnippets() {
        new Documenter(modules).writeModuleCanvases();
    }
}
```

默认会生成到构建目录中的 `spring-modulith-docs` 文件夹。

对重构很有用：重构前生成一次，重构后再生成一次，对比模块关系是否更清晰。

## 2. 具体使用方法：建议按这个顺序落地

### 第一步：引入依赖

Maven 测试验证常用依赖：

```xml
<dependency>
    <groupId>org.springframework.modulith</groupId>
    <artifactId>spring-modulith-starter-test</artifactId>
    <scope>test</scope>
</dependency>
```

如果要使用运行期能力，比如事件发布登记表、Actuator、观测性等，再按需要引入对应 starter，例如官方事件文档列出的：

- `spring-modulith-starter-jpa`
- `spring-modulith-starter-jdbc`
- `spring-modulith-starter-mongodb`
- `spring-modulith-starter-neo4j`

不要一开始就全加。重构第一阶段通常只需要测试依赖和结构验证。

---

### 第二步：写模块结构验证测试

```java
class ModularityTests {

    @Test
    void verifiesModularStructure() {
        ApplicationModules.of(ShopApplication.class).verify();
    }
}
```

先运行它，看失败信息。失败不是坏事，它是在告诉你：项目当前真实依赖关系长什么样。

---

### 第三步：按业务能力整理包结构

优先按业务能力分包，不要按技术层分包。

不推荐：

```text
controller
service
repository
entity
```

更推荐：

```text
order
inventory
payment
user
```

每个业务模块内部可以再有自己的 `controller`、`service`、`repository`：

```text
order
├── web
├── application
├── domain
└── infrastructure
```

关键不是包名必须这样，而是模块边界要围绕业务能力。

---

### 第四步：处理越界依赖

常见处理方式有三种：

1. **把被依赖能力提升为模块 API**：如果其他模块确实应该调用它，就放到模块根包或明确的 API 包。
2. **改成事件协作**：如果只是「某事发生后通知别人」，就发布领域事件或应用事件。
3. **抽出共享基础能力**：如果确实是无业务归属的通用能力，可以放到不属于业务模块的基础包；但要小心 `common` 滥用。

---

### 第五步：加显式约束

等依赖关系清晰后，再用：

```java
@ApplicationModule(allowedDependencies = "inventory")
package com.example.shop.order;
```

然后让 `modules.verify()` 进 CI。

这一步像给架构装护栏：以后有人误依赖内部实现，测试会直接失败。

---

### 第六步：补模块测试和文档

对核心模块增加：

```java
@ApplicationModuleTest
class OrderIntegrationTests {
}
```

对模块关系增加：

```java
new Documenter(ApplicationModules.of(ShopApplication.class))
    .writeModulesAsPlantUml()
    .writeModuleCanvases();
```

这样你能持续回答两个问题：

- 当前模块能不能独立启动？
- 当前模块依赖关系是否符合预期？

---

## 3. 重构现有项目时的最小实践路线

如果你的项目已经存在，建议不要从「完美模块设计」开始，而是从最小闭环开始：

1. 加 `spring-modulith-starter-test`；
2. 写 `ApplicationModules.of(主类).verify()`；
3. 运行测试，记录第一批违规依赖；
4. 画出当前包结构与业务能力映射；
5. 先选一个边界相对清楚的模块试点；
6. 把明显内部实现移入 `internal`；
7. 把真正对外能力留在模块根包或 API 包；
8. 对跨模块副作用改用事件；
9. 加 `@ApplicationModuleTest`；
10. 生成文档，对比重构前后模块图。

不要一上来全项目大搬家。Spring Modulith 最适合做渐进式重构：先让混乱可见，再一块一块收紧。

## 4. 本篇先建立的核心心智模型

可以把 Spring Modulith 理解成三层：

```text
模块模型：ApplicationModules 识别你有哪些模块
结构约束：verify() 检查模块之间有没有越界依赖
协作机制：事件、测试、文档化帮助模块长期保持清晰
```

如果只记一句话：

> Spring Modulith 不是帮你拆微服务，而是帮你把单体应用内部的业务模块边界变成可验证、可测试、可文档化的事实。

## 思考题

1. 你的项目现在更像「按技术层分包」，还是「按业务能力分包」？如果要识别 3-5 个业务模块，你会先列出哪些？
2. 你项目里有没有某个模块直接依赖另一个模块的内部实现？如果有，这种依赖应该提升为 API、改成事件，还是抽成共享基础能力？
3. 如果只能先写一个 Spring Modulith 测试，你会选择 `ApplicationModules.of(...).verify()` 还是 `@ApplicationModuleTest`？为什么？
