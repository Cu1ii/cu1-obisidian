### 你的回答评估

**第 1 题：你的项目现在更像「按技术层分包」，还是「按业务能力分包」？如果要识别 3-5 个业务模块，你会先列出哪些？**

但这里有一个容易混淆的点：

- 「监控平台」本身是产品/业务域；
- `trace`、`metrics`、`logs`、`alert`、`dashboard`、`tenant`、`notification` 这类能力，可以成为业务模块候选；
- 「公共底层能力」不能太早兜底，否则很容易变成新的 `common` 黑洞。

如果你最后发现所有模块都依赖一个巨大公共层，要警惕：它可能不是“基础能力”，而是还没被识别出来的业务能力、平台能力，或者被混在一起的技术适配层。

**第 2 题：有没有某个模块直接依赖另一个模块的内部实现？如果有，应该提升为 API、改成事件，还是抽成共享基础能力？**

⚠️ **部分正确。** 「抽成公共能力」是一种可能，但不是默认答案。

更准确的判断顺序是：

1. 如果被依赖的是某个业务模块拥有的规则或状态，优先**提升为该模块 API**；
2. 如果只是“某事发生后通知别人做副作用”，优先**改成事件**；
3. 只有当它确实无业务归属、稳定、可复用，才**抽成共享基础能力**。

也就是说，公共能力应该是最后的归宿之一，而不是第一个逃生门。

**第 3 题：如果只能先写一个 Spring Modulith 测试，你会选择 `ApplicationModules.of(...).verify()` 还是 `@ApplicationModuleTest`？为什么？**

✅ **正确。** 你选择先跑 `ApplicationModules.of(...).verify()` 是合理的。

原因是：

- 包结构和模块边界还没稳定时，单模块集成测试的收益有限；
- `verify()` 能先暴露真实依赖关系、循环依赖、越界访问；
- 对老项目重构来说，第一步不是证明模块能独立运行，而是先知道边界坏在哪里。

### 正确答案

**第 1 题：** 如何识别业务模块？

> 先从业务能力、生命周期、数据归属、变更原因四个角度识别模块，而不是从 controller/service/repository 这些技术层识别。监控平台里，候选模块可以是 trace、metrics、logs、alert、dashboard、notification、tenant、integration 等。最终是否成模块，要看它是否有相对独立的规则、数据、接口和变更节奏。

**第 2 题：** 越界依赖如何处理？

> 先判断被依赖对象的语义。如果它是被依赖模块对外承诺的一部分，就提升为 API；如果它只是事件发生后的后续动作，就改成事件；如果它是无业务归属的技术能力，才抽成共享基础设施。不要把所有不知放哪的东西都放进 common。

??? 领域事件应该放到包的哪里呢? 因为外界也要能读取到其他模块的领域事件吧

**第 3 题：** 先写哪个测试？

> 老项目重构第一步通常先写 `ApplicationModules.of(主类).verify()`，因为它成本最低，能最快把模块边界问题可视化。`@ApplicationModuleTest` 更适合在模块边界初步稳定后，用来验证某个模块是否能独立启动和协作。

**??? 为什么没有给出怎么引入 spring modulith**

因为第一篇重点是建立心智模型，但这个问题很实际。最小引入方式通常是：

```xml
<dependencyManagement>
  <dependencies>
    <dependency>
      <groupId>org.springframework.modulith</groupId>
      <artifactId>spring-modulith-bom</artifactId>
      <version>${spring-modulith.version}</version>
      <scope>import</scope>
      <type>pom</type>
    </dependency>
  </dependencies>
</dependencyManagement>
```

然后如果只是做模块结构验证、模块测试、文档生成，先加测试 starter：

```xml
<dependency>
  <groupId>org.springframework.modulith</groupId>
  <artifactId>spring-modulith-starter-test</artifactId>
  <scope>test</scope>
</dependency>
```

这里用 `${spring-modulith.version}` 是为了提醒你：实际项目里不要盲目复制固定版本号，要根据当前 Spring Boot 版本与官方兼容矩阵选择 Spring Modulith 版本。

**??? 是指可以额外依赖除 `OrderManagement` 外的 `order.spi` 中的 `OrderCompletedHandler` 吗?**

是的，但要更精确一点：

默认情况下，模块根包是默认 API。例如：

```text
order
├── OrderManagement.java       ← 默认 API
├── spi
│   └── OrderCompletedHandler.java
└── internal
    └── OrderInternalService.java
```

如果你给 `order.spi` 声明：

```java
@org.springframework.modulith.NamedInterface("spi")
package com.example.shop.order.spi;
```

那 `order.spi` 就变成一个额外暴露的“命名接口面”。其他模块可以被允许依赖这个接口面。

配合 `allowedDependencies` 时，可以这样写：

```java
@org.springframework.modulith.ApplicationModule(
    allowedDependencies = "order :: spi"
)
package com.example.shop.inventory;
```

这句话的含义不是“依赖整个 order 模块”，而是“只允许依赖 order 模块暴露出来的 `spi` 这个门”。

所以如果 `OrderCompletedHandler` 在 `order.spi` 里，`inventory` 可以依赖它；但如果 `OrderManagement` 在 `order` 根包，而你只声明了 `order :: spi`，那 `inventory` **不应该**依赖 `OrderManagement`。

**??? 需要额外引入依赖吗**

如果只是使用 Spring 自带的 `ApplicationEventPublisher` 发布事件、普通 `@EventListener` 监听事件，不一定需要额外引入 Spring Modulith 的运行期 starter。

但如果你要使用 Spring Modulith 提供的模块事件能力，例如：

- `@ApplicationModuleListener`；
- 事件发布登记表；
- JDBC/JPA/MongoDB/Neo4j 等持久化事件发布记录；
- 事件测试辅助能力；

就需要按场景引入对应依赖。

一个实用判断是：

```text
只做结构验证 / 文档 / 模块测试：spring-modulith-starter-test
只在业务代码里使用事件 API / @ApplicationModuleListener：spring-modulith-events-api
需要事件发布登记表持久化：spring-modulith-starter-jdbc / jpa / mongodb / neo4j
需要 Actuator/观测性：spring-modulith-starter-insight
```

**??? `spring-modulith-starter-jpa`、`jdbc`、`mongodb`、`neo4j` 的作用是什么呢?**

它们主要不是为了“让 JPA/JDBC 能用”，而是为了给 Spring Modulith 的事件发布登记表等运行期能力提供不同存储实现。

可以粗略这样理解：

| starter                           | 典型作用                                   |
| --------------------------------- | -------------------------------------- |
| `spring-modulith-starter-jdbc`    | 用关系型数据库表保存事件发布记录，适合项目以 JDBC 或关系型数据库为基础 |
| `spring-modulith-starter-jpa`     | 用 JPA 方式接入事件发布登记表，适合已有 JPA 技术栈的项目      |
| `spring-modulith-starter-mongodb` | 用 MongoDB 保存事件发布记录                     |
| `spring-modulith-starter-neo4j`   | 用 Neo4j 保存事件发布记录                       |

对重构第一阶段来说，你不一定需要它们。先用 `spring-modulith-starter-test` 把模块结构跑出来即可。

## 正文内容

第一篇先把 Spring Modulith 理解成“模块边界治理工具”。这一篇进入更具体的问题：

> Spring Modulith 到底如何把一个 Java 包识别成模块？如果默认规则不够用，我应该怎么开门、关门、加白名单？

这几个概念要一起理解：

```text
简单模块：没有复杂子包，根包就是 API
进阶模块：根包是 API，子包默认内部实现
嵌套模块：一个大模块内部再切小模块
开放模块：临时放宽内部访问，方便老项目渐进迁移
命名接口：给模块额外开一个有名字的小门
allowedDependencies：声明本模块允许依赖谁
```

它们不是平行的“功能清单”，而是模块治理从宽到严的工具组合。

---

## 1. 简单模块：直接子包就是模块

Spring Modulith 默认从 Spring Boot 主类所在包往下看。

假设主类在：

```text
com.example.monitoring.MonitoringApplication
```

直接子包是：

```text
com.example.monitoring
├── trace
├── metrics
├── alert
└── dashboard
```

那么 `trace`、`metrics`、`alert`、`dashboard` 通常会被识别为应用模块。

如果某个模块没有复杂子包：

```text
trace
├── TraceQueryService.java
├── TraceIngestionService.java
└── TraceRepository.java
```

这就是简单模块。根包里的 public 类型就是它对外暴露的 API。

适用场景：

- 模块规模小；
- 内部结构还不复杂；
- 暂时不需要区分 `api`、`internal`、`infrastructure` 等子包；
- 想快速建立第一版模块边界。

它的优点是低成本。缺点是模块稍大后，根包会膨胀，很多本来只该模块内部使用的类型也可能被别人看到。

---

## 2. 进阶模块：根包是 API，子包默认内部实现

当模块变复杂，你可能会这样组织：

```text
trace
├── TraceQueryService.java          ← 对外 API
├── TraceIngestionService.java      ← 对外 API
├── internal
│   └── SpanTreeBuilder.java        ← 内部实现
├── infrastructure
│   └── ElasticsearchTraceStore.java← 内部实现
└── web
    └── TraceController.java        ← 内部或入口适配层
```

Spring Modulith 的重要默认规则是：

> 模块根包是 API；根包下面的子包默认是内部实现，其他模块不应该依赖。

??? 对于 cqurs 应该怎么分包呢? 还是说一个包对外提供分别的读写接口, 外部以来通过 packageinfo 来限定引入的依赖?

所以：

```java
// alert 模块里这样依赖，通常是可以的
import com.example.monitoring.trace.TraceQueryService;
```

但：

```java
// alert 模块里这样依赖，就属于越界
import com.example.monitoring.trace.internal.SpanTreeBuilder;
```

这就是第一篇说的 `modules.verify()` 会抓出来的问题。

适用场景：

- 大多数业务模块都适合从这里开始；
- 你希望明确“别人只能用我根包暴露的能力”；
- 模块内部已经有 web/application/domain/infrastructure/internal 等分层。

这里的关键不是子包名字一定叫 `internal`。只要它是模块根包下面的子包，默认就更偏内部。`internal` 只是最直观、最有警示作用的命名。

## 3. `allowedDependencies`：给模块加依赖白名单

默认情况下，一个模块可以依赖另一个模块暴露出来的 API。可是你有时希望更严格：

> `alert` 可以依赖 `trace` 和 `notification`，但不应该依赖 `dashboard`。

这时可以在 `alert` 模块根包加 `package-info.java`：

```java
@org.springframework.modulith.ApplicationModule(
    allowedDependencies = { "trace", "notification" }
)
package com.example.monitoring.alert;
```

含义是：`alert` 模块只允许依赖：

1. `trace` 模块暴露的 API；
2. `notification` 模块暴露的 API；
3. 不属于任何应用模块的代码，例如某些基础配置或第三方库。

如果 `alert` 依赖了 `dashboard`，`verify()` 就会失败。

这一步适合什么时候做？

```text
早期：先不要急着加 allowedDependencies，先让 verify() 暴露真实依赖
中期：确定目标依赖方向后，给核心模块加白名单
后期：把 verify() 放进 CI，让架构约束持续生效
```

一个常见误区是：一开始就给所有模块写严苛白名单。这样往往会让老项目立刻爆出大量失败，但团队还不知道怎么修，最后只能把规则删掉。

更好的方式是：先对一个边界清楚的模块试点，比如 `alert` 或 `notification`。

## 4. `@NamedInterface`：不要打开整扇门，只开一个小门

现在回到你上一篇问的 `order.spi`。

假设 `trace` 模块里有一个接口，其他模块确实需要实现或调用：

```text
trace
├── TraceQueryService.java
├── spi
│   └── TraceEnricher.java
└── internal
    └── DefaultTraceAnalyzer.java
```

如果 `TraceEnricher` 放在 `trace.spi`，默认情况下它属于子包，不应该自动暴露给外部模块。

你可以在 `trace.spi` 下增加：

```java
@org.springframework.modulith.NamedInterface("spi")
package com.example.monitoring.trace.spi;
```

然后在需要依赖它的模块里声明：

```java
@org.springframework.modulith.ApplicationModule(
    allowedDependencies = "trace :: spi"
)
package com.example.monitoring.alert;
```

这表达的是：

> `alert` 不依赖整个 `trace` 模块，只依赖 `trace` 模块名为 `spi` 的接口面。

这比“把 `trace.spi` 放到根包”更干净，因为它保留了语义：这是一个专门开放给别人的扩展点，而不是普通业务服务。

适用场景：

- 一个模块需要暴露扩展点；
- 你不想让别人依赖整个模块 API；
- 你希望依赖关系在 `allowedDependencies` 里表达得更精确；
- 你想避免“为了被依赖而把所有类都挪到根包”。

## 5. 嵌套模块：大模块内部再切小边界

有些模块本身很大，比如 `trace` 下面可能包含：

```text
trace
├── ingestion
├── query
├── retention
└── analysis
```

它们都属于 trace 这个大业务能力，但彼此之间也有内部边界。

这时可以考虑嵌套模块。

```text
trace
├── TraceManagement.java
├── ingestion
│   ├── package-info.java     ← @ApplicationModule
│   └── TraceIngestion.java
├── query
│   ├── package-info.java     ← @ApplicationModule
│   └── TraceQuery.java
└── internal
    └── TraceClock.java
```

嵌套模块适合用来表达：

> 它不是独立到应该成为顶级模块，但在父模块内部又确实需要被治理。

适用场景：

- 一个模块太大，但还不想拆成顶级模块；
- 父模块内部存在多个相对独立子能力；
- 你希望治理父模块内部的依赖方向；
- 比如 `trace.ingestion` 不应该反向依赖 `trace.query`。

不要过早使用嵌套模块。它比简单模块和进阶模块认知成本更高。对于老项目，通常先把顶级模块切清楚，再考虑嵌套。

## 6. 开放模块：老项目迁移时的临时拐杖

开放模块是一个很容易被误用的功能。

你可以这样声明：

```java
@org.springframework.modulith.ApplicationModule(
    type = org.springframework.modulith.ApplicationModule.Type.OPEN
)
package com.example.monitoring.trace;
```

它的效果是：其他模块访问这个模块内部类型时，验证会更宽松。

这对老项目有用，因为一上来要求所有内部包都不能访问，可能会导致成百上千个违规，根本推不动。

但你要把它理解成：

> 开放模块是迁移阶段的安全阀，不是最终架构目标。

适用场景：

- 现有项目内部访问太多，短期无法全部修完；
- 你想先把模块模型建立起来，再逐步收紧；
- 某个遗留模块暂时无法清晰区分 API 与内部实现。

不适用场景：

- 新模块；
- 已经边界清晰的模块；
- 为了图方便长期允许别人访问内部实现。

如果一个系统里大部分模块都是开放模块，那说明你只是“标了模块名”，还没有真正建立边界。

## 7. 怎么选择：四种模块建模方式对比

| 方式 | 核心规则 | 适合阶段 | 风险 |
|---|---|---|---|
| 简单模块 | 直接子包就是模块，根包 public 类型是 API | 起步、小模块 | 根包容易膨胀 |
| 进阶模块 | 根包是 API，子包默认内部实现 | 大多数业务模块 | 需要认真设计 API |
| 嵌套模块 | 父模块内部再建模块边界 | 大模块内部治理 | 过早使用会复杂化 |
| 开放模块 | 放宽内部访问限制 | 老项目渐进迁移 | 容易变成永久妥协 |

对你的监控平台，可以先按这个顺序推进：

```text
第一步：按 trace / metrics / alert / dashboard / notification 识别顶级模块
第二步：每个模块用进阶模块结构，根包只放对外能力
第三步：先不要全量 allowedDependencies，先跑 verify() 看真实依赖
第四步：挑一个边界清晰的模块加 allowedDependencies
第五步：如果 trace 太大，再考虑 trace 内部嵌套模块
第六步：只有遗留依赖太多时，才临时使用开放模块
```

## 8. 一个监控平台示例

假设你有：

```text
com.example.monitoring
├── MonitoringApplication.java
├── trace
│   ├── TraceQueryService.java
│   ├── TraceIngestionService.java
│   ├── spi
│   │   ├── package-info.java
│   │   └── TraceEnricher.java
│   └── internal
│       └── SpanTreeBuilder.java
├── alert
│   ├── package-info.java
│   ├── AlertManagement.java
│   └── internal
│       └── AlertRuleEvaluator.java
└── notification
    ├── NotificationService.java
    └── internal
        └── SmsGatewayAdapter.java
```

`trace.spi.package-info.java`：

```java
@org.springframework.modulith.NamedInterface("spi")
package com.example.monitoring.trace.spi;
```

`alert.package-info.java`：

```java
@org.springframework.modulith.ApplicationModule(
    allowedDependencies = { "trace", "trace :: spi", "notification" }
)
package com.example.monitoring.alert;
```

这表达：

- `alert` 可以查 trace 暴露的 API；
- `alert` 可以使用 trace 暴露的 `spi` 扩展点；
- `alert` 可以调用 notification 暴露的通知能力；
- `alert` 不应该访问 `trace.internal.SpanTreeBuilder`；
- `alert` 不应该依赖 `dashboard`。

如果你想更严格，也可以不允许 `trace` 整体 API，只允许 `trace :: spi`。这取决于 `alert` 到底应该知道多少 trace 能力。

## 9. 本篇核心心智模型

可以把 Spring Modulith 的模块边界想成一栋楼的门禁：

```text
根包 API：正门，默认允许别人走
子包 internal/infrastructure/web：内部房间，默认不让外人进
@NamedInterface：专门开的侧门，有名字、有用途
allowedDependencies：访客白名单，谁能进哪扇门写清楚
OPEN：临时施工通道，迁移期用，用完要拆
```

如果只记一句话：

> 不要把 Spring Modulith 注解当作装饰；它们是在把“谁能依赖谁、能依赖到什么程度”变成可执行的架构规则。

## 思考题

1. 对你的监控平台来说，`trace`、`metrics`、`alert`、`dashboard` 哪些更适合做顶级模块？哪些可能只是某个模块内部的子能力？为什么？
    都适合做顶级模块, 因为都属于某个业务模块
2. 如果 `alert` 现在依赖了 `trace.internal.SpanTreeBuilder`，你会选择：提升为 `trace` API、放进 `trace.spi`、改成事件，还是抽成共享能力？请说明判断依据。
    提升为 API, 说明 alert 需要查询 span tree, 所以需要暴露出一个查询 API 能力
3. 在你的项目里，哪个模块最适合作为第一个 `allowedDependencies` 试点？它应该允许依赖哪些模块？
    我感觉是 alert, 因为他需要查询所有的模块来进行通知
