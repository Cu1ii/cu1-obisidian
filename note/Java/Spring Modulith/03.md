### 你的回答评估

**第 1 题：对你的监控平台来说，`trace`、`metrics`、`alert`、`dashboard` 哪些更适合做顶级模块？哪些可能只是某个模块内部的子能力？为什么？**

⚠️ **部分正确。** 你回答“都适合做顶级模块，因为都属于某个业务模块”，方向是对的，但判断还可以更细。

“属于业务能力”只是成为顶级模块的必要条件之一，不是充分条件。更完整的判断要看：

- 它是否有独立的数据归属；
- 它是否有独立的业务规则；
- 它是否有独立变更节奏；
- 它是否会被多个其他模块使用；
- 它是否能通过清晰 API 与其他模块协作。

比如：

- `trace`、`metrics`、`alert` 通常适合做顶级模块；
- `dashboard` 有时适合做顶级模块，但如果它只是读取多个模块数据并展示，可能更像组合/展示模块；
- 某些 `trace.analysis`、`metrics.query` 可能先作为模块内部子能力，而不是一开始就提升为顶级模块。

**第 2 题：如果 `alert` 现在依赖了 `trace.internal.SpanTreeBuilder`，你会选择：提升为 `trace` API、放进 `trace.spi`、改成事件，还是抽成共享能力？**

✅ **正确。** 你说“提升为 API，因为 `alert` 需要查询 span tree，所以需要暴露查询 API 能力”，这个判断很稳。

更具体地说，不应该让 `alert` 直接知道 `SpanTreeBuilder` 这种内部构造器，而应该由 `trace` 暴露一个稳定查询能力，例如：

```java
public interface TraceQueryService {
    SpanTreeView getSpanTree(TraceId traceId);
}
```

这样 `alert` 依赖的是 `trace` 对外承诺的查询语义，而不是 `trace` 内部如何构建 span tree 的实现细节。

**第 3 题：哪个模块最适合作为第一个 `allowedDependencies` 试点？它应该允许依赖哪些模块？**

⚠️ **部分正确。** 你选择 `alert` 是合理候选，因为它通常是跨模块协作中心。但“它需要查询所有模块来进行通知”这句话要小心。

如果 `alert` 真的同步查询所有模块，它很容易变成新的上帝模块：

```text
alert -> trace
alert -> metrics
alert -> logs
alert -> dashboard
alert -> notification
alert -> tenant
alert -> ...
```

更好的设计通常是：

- `alert` 负责规则、触发条件、告警生命周期；
- `trace` / `metrics` 负责提供必要的查询 API，或发布异常事件；
- `notification` 负责发送通知；
- `alert` 不应该知道太多模块内部细节。

所以 `alert` 可以作为试点，但 `allowedDependencies` 要尽量窄。比如先允许：

```java
@ApplicationModule(
    allowedDependencies = { "trace", "metrics", "notification" }
)
package com.example.monitoring.alert;
```

后续如果发现它依赖太多，就要反问：这些依赖是必要查询，还是应该改成事件？

**第 2 题：** `alert` 依赖 `trace.internal.SpanTreeBuilder` 怎么办？

> 如果 `alert` 需要的是“查询 span tree”这个业务能力，应由 `trace` 暴露查询 API，而不是让 `alert` 依赖内部构造器。只有当 `alert` 是在扩展 trace 的内部流程时，才考虑 `trace::spi`；如果只是 trace 完成后通知 alert，则考虑事件。

## ??? 解答

> 💬 本模块解答你在上一篇中用 `???` / `？？？` 标注的所有困惑。

**??? 那比如说所有的上层都依赖一个数据库表的查询, 那每一个模块还要重复写同样的查询逻辑吗? 这不也是一种冗余和逻辑分散吗**

不应该重复写同样的查询逻辑。模块化不是让你复制代码，而是让你明确**这张表和这段查询能力到底归谁负责**。

你要先判断这个“公共数据库表”是哪种性质：

### 情况 1：它其实属于某个业务模块

比如 `trace_span` 表本质上归 `trace` 模块所有。那么其他模块不应该直接查表，也不应该复制 SQL，而应该依赖 `trace` 暴露的查询 API：

```java
public interface TraceQueryService {
    SpanTreeView getSpanTree(TraceId traceId);
}
```

其他模块调用：

```java
class AlertRuleEvaluator {

    private final TraceQueryService traces;

    AlertRuleEvaluator(TraceQueryService traces) {
        this.traces = traces;
    }

    void evaluate(TraceId traceId) {
        SpanTreeView tree = traces.getSpanTree(traceId);
        // 用查询结果判断是否触发告警
    }
}
```

这样没有重复查询逻辑，也没有跨模块直连数据库表。

### 情况 2：它是多个模块共同需要的参考数据

比如租户、用户、权限、标签、配置字典。这时它可能应该成为独立模块：

```text
tenant
├── TenantQueryService.java
└── internal
    └── TenantMapper.java
```

其他模块依赖 `TenantQueryService`，而不是复制 mapper。

### 情况 3：它只是技术基础设施

比如数据库分页工具、SQL 构造工具、时间处理、ID 生成器。这类可以放在基础设施包里，因为它没有业务归属。

关键判断是：

> 共享的是“技术工具”还是“业务数据访问能力”？

如果共享的是业务数据访问能力，就不要放进 `common.mapper`，而要让拥有该数据的模块暴露查询 API。

**??? 领域事件应该放到包的哪里呢? 因为外界也要能读取到其他模块的领域事件吧**

是的，别的模块要监听事件，就必须能依赖事件类型。因此事件类应该放在**发布方模块对外可见的 API 区域**，而不是 `internal`。

常见放法有两种。

### 放法 A：事件直接放模块根包

```text
trace
├── TraceCompleted.java        ← 对外事件
├── TraceQueryService.java     ← 对外查询 API
└── internal
    └── TraceIngestionService.java
```

适合事件少、模块 API 简单的情况。

### 放法 B：事件放到命名接口包

```text
trace
├── TraceQueryService.java
├── events
│   ├── package-info.java
│   └── TraceAnomalyDetected.java
└── internal
    └── TraceAnalyzer.java
```

`trace.events.package-info.java`：

```java
@org.springframework.modulith.NamedInterface("events")
package com.example.monitoring.trace.events;
```

监听方声明：

```java
@org.springframework.modulith.ApplicationModule(
    allowedDependencies = "trace :: events"
)
package com.example.monitoring.alert;
```

这样表达得更精确：`alert` 不是依赖 `trace` 的全部 API，只是订阅 `trace` 暴露的事件契约。

我更推荐第二种，尤其是事件会变多时。

但要注意：事件是**契约**，不是内部实体。事件里不要塞 JPA Entity、MyBatis DO、内部聚合对象。更推荐不可变、轻量、语义清晰的事件：

```java
public record TraceAnomalyDetected(
    TraceId traceId,
    ServiceName serviceName,
    Duration duration,
    Instant detectedAt
) {}
```

**??? 那我如果使用 mybatis 这种生态, 还能使用 spring-modulith 事件持久化生态依赖吗**

可以。使用 MyBatis 并不妨碍使用 Spring Modulith 的事件发布登记表。

你通常选择 `spring-modulith-starter-jdbc`，因为 MyBatis 项目底层也通常有：

- `DataSource`；
- Spring 事务管理；
- 关系型数据库；
- JDBC 连接能力。

Spring Modulith 的 `jdbc` starter 会用 JDBC 方式维护事件发布记录表，它不要求你的业务数据访问也必须用 Spring Data JDBC。

也就是说：

```text
业务表访问：MyBatis Mapper
事件发布登记表：Spring Modulith JDBC Event Publication Repository
事务边界：Spring 管理的同一个 DataSource / TransactionManager
```

你需要关注的是：

1. 事件发布和业务写入是否在同一个 Spring 事务里；
2. 事件发布登记表的 schema 是否由 Spring Modulith 自动创建，还是由 Flyway/Liquibase 手动管理；
3. 事件对象是否能被 Jackson 正确序列化；
4. 多实例部署时，失败事件重试策略要设计清楚。

如果你不用关系型数据库，而是 MongoDB 或 Neo4j，再考虑对应 starter。MyBatis 场景下，优先看 JDBC。

**??? 对于 cqurs 应该怎么分包呢? 还是说一个包对外提供分别的读写接口, 外部以来通过 packageinfo 来限定引入的依赖?**

这里你已经问到模块 API 设计的关键了。

CQRS 不一定要求你把读写拆成两个顶级模块。更常见的是：一个业务模块内部区分读 API 和写 API。

例如 `trace`：

```text
trace
├── TraceCommandService.java      ← 写入口：开始追踪、补录、标记
├── TraceQueryService.java        ← 读入口：查询 trace、span tree
├── events
│   ├── package-info.java
│   └── TraceAnomalyDetected.java
└── internal
    ├── command
    │   └── TraceCommandHandler.java
    ├── query
    │   └── TraceQueryMapper.java
    └── domain
        └── TraceAggregate.java
```

如果读写 API 都可以对外暴露，放根包即可。

如果你希望更精确控制，例如有些模块只能读 trace，不能写 trace，可以用命名接口：

```text
trace
├── command
│   ├── package-info.java     ← @NamedInterface("command")
│   └── TraceCommandService.java
├── query
│   ├── package-info.java     ← @NamedInterface("query")
│   └── TraceQueryService.java
└── internal
    └── TraceRepository.java
```

然后让 `alert` 只依赖 query：

```java
@ApplicationModule(
    allowedDependencies = "trace :: query"
)
package com.example.monitoring.alert;
```

这表达：

> `alert` 可以查询 trace，但不能调用 trace 的写命令。

但是不要一开始就把所有 API 都拆成命名接口。建议规则是：

```text
默认：根包放少量稳定 API
当你真的需要区分读/写权限时：再拆 query / command 命名接口
当一个模块内部读写复杂到独立演化时：再考虑嵌套模块
```

## 正文内容

前两篇解决了“模块边界怎么建”和“谁能依赖谁”。这一篇解决模块之间协作的第二个核心问题：

> 模块之间到底应该直接调用，还是发布事件？如果发布事件，怎么保证事务边界和可靠性？

Spring Modulith 的事件能力不是为了让你把所有调用都改成事件，而是给你一个更清晰的判断框架。

---

## 1. 直接调用不是坏事，关键看语义

很多人学到事件后，会下意识觉得“模块间直接调用就是耦合，事件才高级”。这是误解。

直接调用适合这类场景：

```text
调用方需要立即得到结果
调用方的业务决策依赖被调用方返回值
失败时调用方必须知道
这件事属于当前用例的主流程
```

例如：`alert` 判断是否触发告警时，需要查询 trace 的 span tree：

```java
class AlertRuleEvaluator {

    private final TraceQueryService traces;

    AlertRuleEvaluator(TraceQueryService traces) {
        this.traces = traces;
    }

    AlertDecision evaluate(TraceId traceId) {
        SpanTreeView tree = traces.getSpanTree(traceId);
        return decideBy(tree);
    }
}
```

这里用事件反而奇怪。因为 `alert` 不是在响应“trace 发生了某事”，而是在主动查询一个决策所需的数据。

所以直接调用的心智模型是：

> 我现在需要你给我一个答案，否则我的业务流程无法继续。

---

## 2. 事件适合表达“某事已经发生”

事件适合这类场景：

```text
发布方完成了自己的业务动作
其他模块可能关心这件事
发布方不应该知道有几个订阅方
订阅方失败不应该破坏发布方代码结构
这件事更像副作用、后续处理、通知或派生流程
```

例如：`trace` 检测到异常链路：

```java
public record TraceAnomalyDetected(
    TraceId traceId,
    ServiceName serviceName,
    Duration duration,
    Instant detectedAt
) {}
```

`trace` 发布事件：

```java
@Component
class TraceAnalyzer {

    private final ApplicationEventPublisher events;

    TraceAnalyzer(ApplicationEventPublisher events) {
        this.events = events;
    }

    void analyze(TraceId traceId) {
        // trace 模块内部完成分析
        events.publishEvent(new TraceAnomalyDetected(
            traceId,
            new ServiceName("payment-service"),
            Duration.ofSeconds(8),
            Instant.now()
        ));
    }
}
```

`alert` 监听事件：

```java
@Component
class AlertOnTraceAnomaly {

    @ApplicationModuleListener
    void on(TraceAnomalyDetected event) {
        // 根据异常 trace 生成告警
    }
}
```

这时 `trace` 不需要知道：

- 谁会创建告警；
- 谁会发送通知；
- 谁会更新 dashboard；
- 未来会不会接 Kafka 或外部系统。

它只表达一件事实：**Trace 异常已经被检测到了**。

---

## 3. 一个判断口诀：查询用调用，事实用事件

可以先用这个粗略规则：

```text
我需要一个答案       → 直接调用
我宣布一件事发生了   → 发布事件
我要强一致地阻止流程 → 直接调用
我要触发后续副作用   → 发布事件
我知道具体下游是谁   → 可以直接调用
我不想知道谁会响应   → 发布事件
```

放到监控平台里：

| 场景 | 推荐协作方式 | 原因 |
|---|---|---|
| `alert` 查询某条 trace 的 span tree | 直接调用 `TraceQueryService` | 需要立即返回结果 |
| `trace` 检测到异常耗时 | 发布 `TraceAnomalyDetected` | 这是事实，多个模块可能关心 |
| `alert` 生成告警后发送通知 | 通常发布 `AlertRaised`，由 `notification` 监听 | 告警生命周期与通知发送解耦 |
| `dashboard` 加载某个用户的告警列表 | 直接调用查询 API 或自己的读模型 | 用户请求需要返回结果 |
| `metrics` 写入新指标后更新聚合视图 | 可发布事件，也可内部处理 | 看聚合视图是否属于同模块 |

这个口诀不是绝对规则，但足够帮助你避免两种极端：

- 所有模块互相直接调用，最后耦合成网；
- 所有东西都变事件，最后流程不可追踪。

## 4. `@ApplicationModuleListener` 到底封装了什么

普通 Spring 事件默认是同步发布的。也就是说：

```java
events.publishEvent(new TraceAnomalyDetected(...));
```

如果监听器是普通同步监听，发布方线程会直接执行监听器逻辑。这可能让事务边界变大。

Spring 里你也可以自己组合：

```java
@Async
@TransactionalEventListener
@Transactional(propagation = Propagation.REQUIRES_NEW)
void on(TraceAnomalyDetected event) {
    // ...
}
```

但这组注解每次写起来很啰嗦，而且团队里容易写得不一致。

Spring Modulith 提供 `@ApplicationModuleListener`，可以把它理解为模块事件监听的推荐快捷方式：

```java
@Component
class AlertOnTraceAnomaly {

    @ApplicationModuleListener
    void on(TraceAnomalyDetected event) {
        // 在独立事务中处理模块事件
    }
}
```

它表达的架构语义是：

> 这是另一个应用模块对当前事件的响应，它应该与发布方主事务解耦，并在自己的事务边界内运行。

这不是说所有监听器都必须用它。你可以这样选择：

| 监听方式 | 适用场景 |
|---|---|
| 普通同步监听 | 必须参与当前事务，失败应让主流程失败 |
| `@TransactionalEventListener` | 等事务提交阶段再处理，但仍想自己控制细节 |
| `@ApplicationModuleListener` | 模块间事件协作的默认推荐方式 |

## 5. 事件发布登记表解决什么问题

现在看一个真实风险。

如果你这样做：

```java
@Async
@TransactionalEventListener
void on(AlertRaised event) {
    notification.send(event);
}
```

它确实把通知发送从主事务里解耦了。但有一个问题：

> 如果主事务提交后，应用刚好宕机，监听器还没来得及执行，这个事件可能就丢了。

或者监听器执行失败：

```text
告警已经创建成功
通知监听器开始执行
短信网关超时
监听器失败
系统没有可靠记录“这个事件还没处理完”
```

事件发布登记表就是为了解决这类问题。

它的基本思路是：

```text
1. 发布业务事件时，为每个事务事件监听器记录一条“待处理发布记录”
2. 监听器成功执行后，把记录标记为完成
3. 如果监听器失败，记录保留为未完成/失败
4. 后续可以由系统或运维逻辑重试、清理、归档
```

可以把它理解成单体内部的轻量 outbox 思路：不是直接把事件扔出去就忘，而是先把“这个事件需要被谁处理”记下来。

Spring Modulith 官方文档中，事件发布登记表会为事务事件监听器创建发布日志；监听器成功后记录完成，失败则保留，以便后续重试或管理。

## 6. 在 MyBatis 项目里的可靠事件协作落地

假设你的监控平台使用 MyBatis，推荐的最小路径是：

### 第一步：业务数据继续用 MyBatis

```java
@Mapper
interface AlertMapper {
    void insert(AlertRecord record);
}
```

### 第二步：引入 Spring Modulith JDBC starter

```xml
<dependency>
  <groupId>org.springframework.modulith</groupId>
  <artifactId>spring-modulith-starter-jdbc</artifactId>
</dependency>
```

这不是让你把业务查询改成 Spring Data JDBC，而是让 Spring Modulith 用 JDBC 维护事件发布登记表。

### 第三步：发布事件

```java
@Component
class AlertManagement {

    private final AlertMapper mapper;
    private final ApplicationEventPublisher events;

    AlertManagement(AlertMapper mapper, ApplicationEventPublisher events) {
        this.mapper = mapper;
        this.events = events;
    }

    @Transactional
    void raise(AlertCommand command) {
        AlertId alertId = AlertId.newId();
        mapper.insert(AlertRecord.from(alertId, command));

        events.publishEvent(new AlertRaised(
            alertId,
            command.level(),
            Instant.now()
        ));
    }
}
```

### 第四步：其他模块监听

```java
@Component
class NotifyOnAlertRaised {

    @ApplicationModuleListener
    void on(AlertRaised event) {
        // 调用短信、邮件、企微、Webhook 等通知渠道
    }
}
```

这个结构里：

```text
alert 业务写入：MyBatis
AlertRaised 事件：Spring 事件机制
事件可靠记录：Spring Modulith JDBC registry
通知处理：@ApplicationModuleListener
```

你不用为了 Spring Modulith 抛弃 MyBatis。

## 7. 事件设计的三个常见误区

### 误区 1：事件名像命令

不推荐：

```java
public record SendAlertNotification(AlertId alertId) {}
```

这更像在命令别人做事。

更推荐：

```java
public record AlertRaised(AlertId alertId, AlertLevel level, Instant raisedAt) {}
```

事件应该表达已经发生的事实，而不是命令下游执行动作。

### 误区 2：事件里塞太多内部对象

不推荐：

```java
public record AlertRaised(AlertEntity entity) {}
```

这会泄露内部持久化模型，也增加序列化风险。

更推荐：

```java
public record AlertRaised(
    AlertId alertId,
    AlertLevel level,
    String ruleName,
    Instant raisedAt
) {}
```

事件只携带下游稳定需要的信息。下游如果需要更多详情，可以再调用发布方查询 API。

### 误区 3：用事件隐藏本该建模的依赖

如果 `alert` 必须在规则判断时查询 `trace`，那就直接依赖 `TraceQueryService`。不要绕一圈发布事件再等待某个异步结果。

事件不是为了消灭依赖，而是为了表达另一类依赖：

> 我不需要你现在给我答案；我只是告诉你，一件值得关心的事发生了。

## 8. 本篇核心心智模型

可以把模块协作分成两种语义：

```text
直接调用：我需要你现在回答我
应用事件：我告诉大家一件事已经发生
```

再加上可靠性层：

```text
@ApplicationModuleListener：让模块事件监听有清晰事务边界
Event Publication Registry：记录事件投递状态，失败后可恢复
JDBC/JPA/MongoDB/Neo4j starter：选择事件发布记录保存在哪里
```

如果只记一句话：

> Spring Modulith 的事件不是为了把代码写得“更异步”，而是为了把模块间的副作用协作变成有边界、可恢复、可治理的事实。
