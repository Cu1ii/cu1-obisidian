# 第 1 课：先把 review-agent 第一版边界钉死

> 前置知识：AI 工程基础；Prompt 基本结构；代码 review 基本概念
> 难度：入门
> 预计阅读时间：18 分钟

## 正文内容

这门课不再停留在“什么是 Agent”，而是直接开始搭一个 **可落地、可评估、可迁移** 的 `review-agent`。

第一课只做一件事：

> **把第一版要做什么、不做什么，钉死。**

很多 AI 项目做不出来，不是因为模型不够强，而是因为第一版边界太松：

- 一上来想支持所有语言
- 一上来想同时抓 correctness、security、style、性能、架构
- 一上来想自动修复、自动评论、自动合并
- 一上来想“尽量多报一点”

结果就是：**误报爆炸，信任崩掉，根本没法评估。**

所以第一版最重要任务，不是“尽可能强”，而是：

> **范围小，但结果可信。**

### 1. 第一版目标：不是“万能评审”，而是“高 Precision 的 Java 增量审查器”

你这门课的第一版目标，可以先写成一句工程定义：

> **输入一段 Java diff，输出一组有证据支撑的 correctness / security findings。**

这句话里，已经藏了 4 个关键收缩动作。

#### 收缩 1：只看 Java

因为不同语言的风险结构完全不同。

Java 常见高价值问题，往往集中在：

- 空指针与判空顺序
- 集合、流、Optional 误用
- 并发与线程池使用
- 事务边界
- 资源关闭
- 权限、输入校验、敏感信息处理

如果你把 TypeScript、Python、Go 一起混进来，第一版规则会立刻失控。

所以这里先明确：

> **第一版不做多语言，先把 Java 做实。**

#### 收缩 2：只看增量 diff，不做全仓扫描

第一版 review-agent 不是静态分析平台，也不是 SAST。

它更像一个“PR 审查助手”：

- 主要输入是 diff
- 必要时补读少量上下文文件
- 重点判断“这次改动是否引入高风险问题”

这和“扫全仓所有历史问题”是两件事。

全仓扫描有几个坏处：

- 上下文太大，成本太高
- 历史遗留问题会污染本次评审
- 很多问题和本次改动无关
- 用户难以判断 finding 是否该由当前 PR 负责

所以第一版默认工作对象应是：

> **一段增量代码变更，而不是整个仓库。**

#### 收缩 3：只抓 correctness + security，不碰 style

这是你已经明确的偏好，也是对的。

因为 style 很容易产生噪声。

比如这些内容：

- 命名不够优雅
- 注释不够统一
- if/else 可改写
- 某段代码“看起来”不够简洁

这些在第一版里几乎都会降低信噪比。

而 correctness / security 更适合做第一版，原因是它们更容易绑定**客观失败后果**：

- 会抛异常吗？
- 会写错数据吗？
- 会导致并发问题吗？
- 会越权吗？
- 会泄露敏感信息吗？
- 会绕过校验吗？

一句话：

> **第一版先报“会出事”的问题，不报“可以更优雅”的问题。**

#### 收缩 4：优先 Precision，不优先 Recall

这是最容易说、最难真正做到的点。

很多人会说：“宁可多报，不要漏报。”

这句话在第一版 review-agent 上，通常是错的。

为什么？

因为代码评审场景里，**误报比漏报更伤信任**。

假设 Agent 连报 8 条，结果 6 条站不住脚。用户很快会形成稳定印象：

> 这玩意儿废话多，不能信。

一旦信任崩掉，后面即使它偶尔报对真问题，也没人想认真看。

所以第一版策略应该反过来：

> **少报，但每一条都尽量拿得出证据。**

也就是：

- 不确定，宁可不报
- 没有足够上下文，先补上下文，不急着下结论
- 只有“最佳实践建议”，不报
- 只有模糊风险联想，不报
- 只有在特定业务前提下才成立的问题，默认不报

### 2. 一次 review 任务，到底由什么组成

现在把一次 review 任务拆开。第一版至少有 4 个部分：

```text
输入 → 上下文 → 约束 → 输出
```

这 4 段比“给模型一个 Prompt”更接近真实工程。

### 2.1 输入：最小必需材料是什么

第一版最核心输入，不是整仓代码，而是：

```text
Java diff
```

比如：

- 改了哪些文件
- 哪些行被删除 / 新增
- 新增代码是什么
- 变更附近原始上下文是什么

这里先建立一个非常重要判断：

> **没有 diff，就没有 review。**

因为 review-agent 不是知识问答机器人，它的工作对象必须是**变更**。

### 2.2 上下文：为什么不能只看 diff

只看 diff，很多时候不够。

例子：

```java
executor.submit(() -> childExecutor.submit(task));
```

只看这一行，你能怀疑“父子线程池嵌套可能有风险”。
但你还不能立刻下结论。

因为你还不知道：

- `executor` 和 `childExecutor` 是不是同一个池
- 队列、拒绝策略是什么
- 任务里是否阻塞等待
- 调用链上是否存在 `Future.get()` / `join()`
- 业务吞吐和线程模型是什么

所以第一版不能把“看到可疑模式”直接等于“可以报 finding”。

它中间还缺一步：

> **补上下文。**

也就是说，Agent 工作流至少要允许：

- 读变更文件的局部上下文
- 查被调用方法定义
- 看相关类字段 / 初始化方式
- 必要时看配置或安全边界代码

因此，review-agent 不是“看一段文本然后输出意见”，而是：

> **先看 diff，再按需取证。**

### 2.3 约束：什么情况下不允许报

这是第一版能不能稳的关键。

很多失败项目，不是不会报，而是**没有“不报”的规则**。

你要先给 Agent 加刹车。

第一版至少需要 4 条硬约束：

#### 约束 1：没有明确失败后果，不报

比如“这段代码好像有点绕”“这里可能会有性能问题”“这种写法未来可能不太好维护”。

这些都不属于第一版重点。

第一版只关心：

- 明确错误结果
- 明确安全后果
- 明确约束被绕过

#### 约束 2：没有足够证据，不报

看到模式像 bug，不等于它就是 bug。

例如：

- 怀疑 NPE，但上文可能已经判空
- 怀疑越权，但网关层可能已经鉴权
- 怀疑资源泄露，但外层可能有统一关闭

所以第一版要强制区分两件事：

- **可疑信号**
- **可提交 finding**

只有后者能进最终输出。

#### 约束 3：只报改动引入或改动暴露的问题

如果某文件原来就有老问题，而这次 PR 没碰到，第一版默认不报。

因为否则会发生：

- 用户无法判断优先级
- 责任归属混乱
- 当前 PR 噪声暴增

第一版核心问题应是：

> **这次改动，带来了什么新的 correctness / security 风险？**

#### 约束 4：输出必须能落到具体代码位置

不能写这种话：

- “整体看起来可能不安全”
- “这里并发上需要小心”
- “建议进一步检查权限控制”

这类说法没法被工程使用。

一条合格 finding，至少要能指出：

- 哪个文件
- 哪段改动
- 什么问题
- 为什么成立
- 会导致什么结果

### 2.4 输出：第一版不是“评论风格”，而是“缺陷报告”

所以你应该把输出理解成 **结构化 findings**，不是自然语言散文。

输出未来至少要容纳这些信息：

- 位置
- 问题类型
- 严重级别
- 结论
- 证据
- 失败场景
- 修复方向

你现在先不用急着背字段名。

第一课只记住一句：

> **review-agent 最终产物不是“说点看法”，而是“提交缺陷记录”。**

### 3. 第一课结论：先把地基压实

做第一版 review-agent，最先要锁死 4 个决定：

```text
语言：Java
对象：增量 diff
范围：correctness + security
策略：高 Precision，证据不足不报
```

这 4 个决定，就是第一版所有后续设计的地基。

后面你写规则、写 Prompt、写 schema、做样本评估，都会不断回到这 4 句话。

如果这 4 句不稳，后面所有“技巧优化”都会变成空转。

1. 为什么第一版 review-agent 不应该同时处理 correctness、security、style、性能、架构建议？请从“信噪比”和“评估可行性”两个角度回答。
2. 为什么“看到可疑模式”不等于“可以直接报 finding”？请结合“补上下文”解释。
3. 假设某个 PR 只改了一个接口参数校验，但文件里原本还存在一个老的线程安全问题。第一版 review-agent 为什么默认不报这个老问题？
