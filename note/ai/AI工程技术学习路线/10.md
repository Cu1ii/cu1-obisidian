**第 1 题：第一周打算选哪 5 个真实 PR 跑评估？为什么？**

⚠️ 部分正确。

你写：

> 我会找 5 个开源项目

方向对，但题目要的是「5 个真实 PR」，不是「5 个项目」。

如果只说项目，还不够落地。评估样本最终要落到**具体 PR / 具体 diff**，因为 review Agent 分析的是变更，不是整个仓库。

更好的选法不是随便找 5 个 PR，而是按**样本覆盖面**选：

1. 一个空指针 / nil pointer 类 PR。
2. 一个并发风险类 PR，比如线程池、锁、共享变量。
3. 一个资源泄漏类 PR，比如流 / 连接 / 锁释放。
4. 一个安全风险类 PR，比如 SQL / 命令注入或权限校验缺失。
5. 一个负样本 PR，比如只改日志、注释、变量名，不应报高置信度 finding。

这样你第一周拿到的不是「5 个随便的 PR」，而是**最小评估集雏形**。

**第 2 题：如果 Claude Code 与 Codex 在同一个样本上 Precision 差 20%，你会怎么定位原因？**

❌ 未完成。

你写：

> 没啥思路...

这很正常。因为这题本质是平台对比实验设计，需要把差异拆成变量。

定位思路应该是：

1. 先固定输入：同一个 diff、同一套规则、同一个 schema。
2. 再固定 Prompt：system prompt 和 workflow 文本完全一致。
3. 再看工具差异：两个平台读了哪些文件、读文件顺序是否不同、读到的上下文是否不同。
4. 再看模型差异：模型本身不同，温度、结构化输出支持、token 限制是否不同。
5. 再看过滤差异：平台是否自动加系统规则、自动裁剪上下文、自动总结历史。
6. 最后看输出差异：误报是因为幻觉、上下文不足、工具缺失，还是规则没执行严。

所以平台对比不是「哪个更聪明」，而是**同一实验条件下，哪个链路更稳定**。

### 正确答案

**第 1 题：第一周的 5 个 PR 样本如何选**

> 不是先找 5 个项目，而是从开源项目中挑 5 个代表性 PR / diff。
>
> 样本覆盖建议：
> 1. Java 空指针问题
> 2. Go 并发风险问题
> 3. 资源泄漏问题
> 4. 安全风险问题
> 5. 负样本 PR（日志 / 命名 / 注释变更）
>
> 这样第一周就有正样本、负样本和类别覆盖。

**第 2 题：Claude Code 与 Codex Precision 差 20% 时如何定位**

> 第一步，固定变量：同一 diff、同一规则、同一输出 schema。
>
> 第二步，对比上下文：两个平台分别读了哪些文件、哪些上下文。
>
> 第三步，对比模型设置：模型名、temperature、最大上下文、结构化输出能力。
>
> 第四步，对比平台封装：是否自动裁剪历史、自动加入系统规则、自动限制工具。
>
> 第五步，对比 findings：是误报多、漏报多，还是证据不足。
>
> 目标不是“凭感觉选平台”，而是找出 Precision 差异来自哪一层。

**第 3 题：用 5 段式描述你的项目**

> 输入：PR diff、目标分支、仓库内相关文件、评审规则、历史样本。
>
> 模型：根据规则和上下文，对增量代码做结构化 review，输出高置信度 findings。
>
> 工具：读取 diff、读取文件、搜索调用链、读取静态分析结果、运行只读检查。
>
> 评估：用正样本 / 负样本 / 边界样本计算 Precision、Recall、误报率、成本和耗时。
>
> 交付：Markdown / HTML / PR comment 形式的 review 报告，可在 Claude Code、Codex 或自建系统里复用。

## ??? 解答

**??? 我的结构目录是像下面这样的，你上面的目录结构会影响我当前结构吗**

不会直接影响。上篇给的是**你自己项目仓库**里的建议目录，不是要改你当前 `.claude/` 目录结构。

你现在这套：

```text
.claude/
├── agents
├── commands
├── settings.json
└── skills
```

这是 Claude Code / 本地 skill 配置目录，作用偏「平台配置」。

我建议的：

```text
review-agent/
├── rules/
├── prompts/
├── workflows/
├── eval/
├── reports/
└── platform/
```

是你**代码 review 项目本身**的业务目录，作用偏「平台无关资产」。

两者关系：

- `.claude/`：Agent 平台怎么跑。
- `review-agent/`：你的 review 规则、schema、评估集、报告模板放哪里。

所以不会冲突。你甚至可以这样放：

```text
your-project/
├── .claude/
└── review-agent/
```

或者如果你想更贴近 Claude Code 生态，也可以把它放进：

```text
.claude/review-agent/
```

但从**迁移到 Codex**角度，我更建议放在 `.claude/` 外面。因为 `.claude/` 很容易让这些资产被误认为是 Claude 专属配置，不利于迁移。

一句话：

> **建议把“平台配置”和“业务资产”分开。**

**??? 这部分不能随着 agent 引入而自动引入吗**

你问得很对。答案是：**有些能自动引入，有些不能。**

### 能被 Agent 平台自动带上的

- 工具调用能力
- 权限提示机制
- 基础循环控制
- 会话状态管理的一部分
- 文件读取 / 搜索 / 命令执行入口

这些是平台层能力，Claude Code / Codex 会帮你封装。

### 不能自动替你解决的

- 你的 review 业务规则是什么
- 哪些 finding 算高置信度
- 哪些类别要审，哪些不审
- 你的输出 schema 长什么样
- 你的评估样本怎么设计
- 你的报告怎么渲染
- 你的 Precision / Recall 怎么对比
- 你的缓存 key 设计
- 你的平台迁移兼容策略

这些是**业务层和工程层资产**，平台不会自动替你做对。

所以：

> **Agent 平台能自动带来执行能力，但带不来你的业务标准。**

你真正要沉淀的，不是“怎么调用 Claude Code”，而是：

1. review-rules
2. output-schema
3. workflow
4. eval samples
5. render template

这些才是可迁移资产。

如果你只依赖平台自动行为，一换平台，效果可能就散了。
