## 正文内容

你说「模型调用解释不出来」，这非常关键。因为 AI 工程所有后续能力——Prompt、RAG、Agent、评估、成本优化——都站在「一次模型调用」之上。

先给结论：

> **一次模型调用，本质是：工程系统把上下文组织成消息，发送给模型；模型根据上下文预测下一段最合适的文本或结构化动作；系统再解析输出并决定下一步。**

这句话拆开，有 6 个核心环节：

1. Message：系统把信息装进消息。
2. Token：模型看到的不是字，而是切分后的 token。
3. Context Window：模型只能看见上下文窗口里的内容。
4. Generation：模型逐步生成输出。
5. Parameters：参数影响稳定性、发散程度和长度。
6. Parsing：系统把模型输出变成可用结果。

---

## 一、Message：模型不是直接读你的心，它读消息列表

很多人以为调用模型就是发一句话：

```text
帮我总结这篇文章。
```

工程上更准确的形式是：发送一组 **messages**。

典型结构像这样：

```json
[
  {
    "role": "system",
    "content": "你是一个严谨的技术文档助手，回答必须基于给定材料。"
  },
  {
    "role": "user",
    "content": "请总结下面这篇文章：..."
  }
]
```

这里最重要的是 `role`。

### 1. system：定义模型应该扮演什么规则

`system` 常放高优先级约束，例如：

- 你是什么角色
- 回答风格
- 禁止做什么
- 输出格式
- 安全边界
- 遇到不确定信息怎么办

例子：

```text
你是一个代码审查助手。只指出会导致 bug、性能问题或安全风险的点。不要评价命名风格。
```

这会把模型从「泛泛聊天」收束成「代码审查」。

### 2. user：用户当前真正提出的任务

`user` 放当前请求，例如：

```text
审查下面这段代码，找出可能导致空指针异常的位置。
```

用户问题要清楚，最好包含目标、材料和输出要求。

### 3. assistant：历史中模型以前说过什么

多轮对话里，历史回答会作为 `assistant` 消息重新传给模型。

注意一个工程事实：

> **模型通常没有真正的长期记忆。所谓「记得上下文」，是因为系统把历史消息再次放进了本次请求。**

这点非常重要。它解释了为什么上下文太长会贵、会慢，也解释了为什么历史对话可能污染当前回答。

---

## 二、Token：模型看到的单位不是汉字或单词

模型不会直接按「一个汉字」「一个英文单词」理解文本，而是先把文本切成 **token**。

你可以粗略理解为：

> **Token 是模型处理文本的基本单位。**

例如英文里，`unbelievable` 可能被切成几个 token；中文里，一个词、一段标点和多个字符也可能被切成不同 token。

工程上为什么要关心 token？

因为它影响 3 件事：

1. **上下文长度**：请求能塞多少材料。
2. **成本**：很多模型按输入 token 和输出 token 计费。
3. **延迟**：输入越长、输出越长，通常越慢。

所以 AI 工程不是「把所有资料都塞给模型」。更成熟的做法是：只给当前任务真正需要的信息。

---

## 三、Context Window：模型只看窗口内的信息

**上下文窗口**指一次模型调用最多能处理多少 token。

如果窗口是 100k token，不代表你应该每次都塞满 100k token。

因为塞太多会带来问题：

- 成本变高
- 延迟变长
- 关键信息被淹没
- 模型更容易忽略细节
- 日志和调试更困难

这就是为什么后面要学 RAG。RAG 本质不是「炫技」，而是解决一个朴素问题：

> **材料太多时，先检索出最相关片段，再交给模型回答。**

但在学 RAG 前，先记住：模型不会自动知道你文件夹里、数据库里、网页里的内容。除非系统把这些内容放进上下文，或者给模型工具去查。

---

## 四、Generation：模型输出是一步步生成的

模型生成回答时，不是先在脑子里写完整篇，再一次性吐出来。

更接近这样：

1. 读入上下文。
2. 预测下一个 token。
3. 把这个 token 加入已生成内容。
4. 再预测下一个 token。
5. 重复，直到停止。

这解释了两个常见现象。

### 现象 1：为什么它会胡说？

因为模型的目标不是「查证世界真相」，而是在上下文和参数约束下生成看起来最合理的内容。

如果上下文没有事实依据，模型仍可能生成流畅但错误的答案。

所以工程上要做：

- 给足依据
- 要求引用来源
- 限制回答范围
- 不知道时允许说不知道
- 用评估集发现幻觉

### 现象 2：为什么同样问题答案会变？

因为生成过程可以带随机性。参数不同，输出稳定性不同。

这就进入下一个部分。

---

## 五、Parameters：参数不是装饰，是行为控制旋钮

先掌握 3 个常见参数。

### 1. temperature：控制发散程度

`temperature` 越低，输出越稳定、越保守。

`temperature` 越高，输出越发散、越有创造性。

工程判断：

- 信息抽取、分类、格式转换：通常用低 temperature。
- 写广告文案、头脑风暴：可以用高一点。
- 代码修复、事实问答：倾向低一点。

### 2. max_tokens：控制最长输出

`max_tokens` 限制模型最多生成多少 token。

如果设置太小，答案可能被截断。

如果设置太大，成本和延迟会增加。

工程上常见策略：根据任务设合理上限，而不是无限放开。

### 3. stop：告诉模型到哪里停

`stop` 可以指定停止标记。

例如你只想让模型生成 JSON，不希望它继续解释，可以配合输出格式约束和停止条件。

不过现代 API 里，更推荐使用结构化输出能力，而不是只靠 stop 字符。

---

## 六、Parsing：模型回答还不是工程结果

模型输出是一段文本，系统要把它变成可用结果。

比如你要模型抽取用户意图：

```json
{
  "intent": "refund_request",
  "order_id": "12345",
  "confidence": 0.82
}
```

系统不能只相信「它看起来像 JSON」。还要做校验：

- 是否是合法 JSON？
- 字段是否齐全？
- `intent` 是否在允许枚举里？
- `confidence` 是否是数字？
- `order_id` 是否符合格式？

这就是 AI 工程和玩 Demo 的区别。

玩 Demo：模型输出看起来对就行。

做工程：模型输出必须能被系统安全解析、校验、兜底。

---

## 七、一次模型调用的工程流程

把上面串起来，一次模型调用可以画成这样：

```text
用户请求
  ↓
收集上下文：用户输入、历史消息、业务数据、权限、文件
  ↓
组装 messages：system / user / assistant
  ↓
设置参数：temperature、max_tokens、输出格式等
  ↓
发送 API 请求
  ↓
模型逐 token 生成输出
  ↓
解析输出：文本、JSON、工具调用参数
  ↓
校验结果：格式、权限、事实依据、业务规则
  ↓
返回用户或进入下一步工具调用
```

你只要真正理解这条链路，后面很多概念会变清楚：

- Prompt 工程 = 更好地组装 messages 和上下文。
- RAG = 在组装 messages 前，先检索相关材料。
- Agent = 模型输出不只是答案，还可能决定下一步调用什么工具。
- 评估 = 检查这条链路在固定样本上是否稳定表现好。
- 成本优化 = 控制输入 token、输出 token、模型选择和调用次数。

## 八、最小可复用 Prompt 结构

现在先给一个基础结构，不要求背，先建立形状感：

```text
# 角色
你是……

# 任务
你需要完成……

# 输入材料
以下是你可以使用的材料：
……

# 约束
- 只能基于输入材料回答
- 不确定时说「资料不足」
- 不要编造不存在的信息

# 输出格式
请按以下 JSON 格式输出：
{
  "answer": "...",
  "evidence": ["..."],
  "confidence": "high | medium | low"
}
```

这不是万能模板，但体现了工程思维：

- 角色：收束行为。
- 任务：定义目标。
- 输入材料：给事实依据。
- 约束：减少跑偏。
- 输出格式：方便系统解析。

如果只写「帮我回答一下」，模型可能能答，但系统很难稳定复现。

## 九、你目前最该掌握的一句话

> **模型调用不是魔法，而是一次带上下文、参数和输出校验的远程函数调用。只是这个函数内部有概率性，会生成自然语言。**

把它看成函数，你会问：

- 输入是什么？
- 输出是什么？
- 出错怎么办？
- 是否可重试？
- 是否可测试？
- 成本多少？
- 权限边界在哪里？

这就是 AI 工程师的视角。
