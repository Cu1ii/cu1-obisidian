## ??? 解答

**??? 这个只是 agent 内部输出结构？最终输出结构我理解应该是个 HTML 格式？**

对，你理解对一半。要分两层：**内部结构**和**最终展示**。

### 1. Agent 内部输出结构

内部结构要给程序用，所以要稳定、可解析、可校验。

例如：

```json
{
  "file": "src/main/java/OrderService.java",
  "line": 42,
  "severity": "HIGH",
  "category": "NULL_POINTER",
  "evidence": "orderRepository.findById(id) 可能返回 empty，但后续直接 get()",
  "suggestion": "使用 orElseThrow 或显式处理 empty"
}
```

这层像数据库记录或 DTO。它不是最终给用户看的样子。

### 2. 最终输出结构

最终输出可以是 HTML、Markdown、GitHub PR comment、IDE 插件面板、JSON API 响应。

例如 HTML：

```html
<div class="finding high">
  <h3>高风险：可能的空指针问题</h3>
  <p><strong>文件：</strong>src/main/java/OrderService.java:42</p>
  <p><strong>证据：</strong>orderRepository.findById(id) 可能返回 empty，但后续直接 get()</p>
  <p><strong>建议：</strong>使用 orElseThrow 或显式处理 empty</p>
</div>
```

工程链路是：

```text
模型结构化输出 JSON
  ↓
程序解析成 ReviewFinding 对象
  ↓
校验、过滤、排序、去重
  ↓
渲染成 HTML / Markdown / PR 评论 / IDE 面板
```

关键点：**不要让模型直接生成最终 HTML 作为唯一结果**。

原因：

- HTML 难做业务校验。
- 字段缺失不容易发现。
- XSS 风险更高。
- 同一条 finding 难去重。
- 难转成 PR comment 或 IDE 面板。

更稳做法：模型输出结构化 finding；系统负责渲染。

## 一、为什么 Claude Code 看起来像「提示词驱动」

你输入：

```text
帮我 review 当前 diff，只找高置信度 bug，不要管格式问题。
```

Claude Code 可能会：

1. 读取 git diff。
2. 搜索相关文件。
3. 读取调用方和被调用方。
4. 分析代码。
5. 运行测试或命令。
6. 汇总 findings。
7. 给出报告。

你只写了 Prompt，但它做了很多事。

原因不是 Prompt 本身有魔法，而是平台提供了能力：

```text
Prompt：定义任务目标和约束
模型：做理解、规划、判断、生成
工具层：读文件、搜索、跑命令、查 git
权限层：决定哪些工具能用，哪些要确认
状态层：记录已经看过什么、下一步做什么
控制层：决定继续、停止、重试、报错
展示层：把结果输出给用户
```

你看到的是 Prompt，没看到的是平台工程。

## 二、封装型 Agent 和自建 Agent 的区别

### 封装型 Agent

代表：Claude Code、Codex、Cursor、IDE Agent。

特点：

- 工具系统已经内置。
- 文件读取、搜索、命令执行已经封装。
- 权限提示已经有现成机制。
- 对话状态由平台管理。
- 适合个人开发、半自动辅助、快速原型。

你主要控制：

- 提示词
- 规则文件
- 工作流步骤
- 评估标准
- 输出格式

### 自建 Agent

代表：你自己写一个代码 review 服务。

特点：

- 工具要自己接。
- 状态要自己存。
- 权限要自己控。
- 缓存要自己做。
- 成本要自己算。
- 展示要自己设计。
- 适合团队服务、产品化、可审计、可集成 CI。

你要负责完整工程链路。

### 对比表

| 维度 | 封装型 Agent | 自建 Agent |
|---|---|---|
| 上手速度 | 快 | 慢 |
| 工具能力 | 平台内置 | 自己实现 |
| 权限控制 | 平台提供一部分 | 自己全负责 |
| 定制能力 | 受平台限制 | 高 |
| 可观测性 | 取决于平台 | 可完全设计 |
| 成本控制 | 部分可控 | 完全可控 |
| 适合场景 | 个人效率、原型 | 团队产品、CI 集成 |

## 三、你做代码 review 能力，建议分两阶段

不要一上来就自建完整 Agent。太重。

更好的路线：

### 阶段 1：基于 Claude Code 做 Review Workflow

目标：验证「什么样的 review 有价值」。

你可以先定义 review 规则：

```text
只找以下问题：
1. 空指针 / nil pointer
2. 资源泄漏
3. 并发安全问题
4. SQL / 命令注入
5. 明显业务逻辑错误

不要输出：
1. 命名建议
2. 排版建议
3. 主观风格建议
4. 没有证据的猜测
```

再定义工作流：

```text
1. 读取当前 git diff。
2. 找出变更文件。
3. 对每个变更文件读取必要上下文。
4. 只输出高置信度 finding。
5. 每条 finding 必须包含文件、行号、严重级别、证据、修复建议。
6. 如果没有高置信度问题，输出“未发现高置信度问题”。
```

这阶段你不用实现工具层，因为 Claude Code 已经有。

你要练的是：规则、Prompt、样本、评估。

### 阶段 2：抽象成自己的 Review Agent 服务

当你知道什么 review 规则有效后，再考虑自建。

自建服务可以包含：

- Git diff 获取模块
- 文件上下文检索模块
- 静态分析模块
- 模型 review 模块
- finding 验证模块
- 缓存和成本控制模块
- HTML / PR comment 展示模块
- 评估集和指标模块

这时前面讲的复杂工程才必要。

## 四、为什么现在还要学复杂工程

你可能会问：既然 Claude Code 已经封装了，我为什么还要学状态、工具、限流、缓存？

因为你要能判断边界。

例如你用 Claude Code review 代码时，它输出一个 bug，你要判断：

- 它是不是读到了足够上下文？
- 它有没有只看 diff 没看调用方？
- 它是不是把测试失败误判成代码 bug？
- 它是不是提出了风格建议而非真实 bug？
- 它有没有重复读同一块内容？
- 它有没有因为上下文太长漏掉关键条件？
- 它的结果能不能转成结构化 finding？

这些判断都来自工程层理解。

你可以不一开始自建，但不能不懂它怎么工作。

## 五、评估：代码 review 能力不能靠感觉

进入最后一个大模块：评估、部署与迭代。

先讲评估。

> **AI 代码 review 的目标不是“看起来很聪明”，而是“高置信度发现真实问题，同时尽量少打扰用户”。**

代码 review Agent 最怕两种失败：

1. **漏报**：真实 bug 没发现。
2. **误报**：不是 bug，却说成 bug。

误报太多，用户会不信。漏报太多，系统没有价值。

### 评估指标

至少要看 5 个指标：

1. **Precision（准确率）**：输出的问题里，有多少是真的。
2. **Recall（召回率）**：真实问题里，有多少被找到了。
   ??? 召回率是什么, 他是衡量什么的指标
3. **False Positive Rate（误报率）**：多少 finding 是噪声。
4. **Time Cost（耗时）**：完成一次 review 要多久。
5. **Token / Money Cost（成本）**：一次 review 花多少模型成本。

对 MVP 来说，先优先 Precision。

原因：代码 review 工具误报太多，用户会立刻弃用。

所以第一版策略是：**宁可少报，也不要乱报。**

## 六、离线评估集怎么做

离线评估集就是固定一批代码变更，用来测试 Agent 能力。

代码 review Agent 的评估集可以这样设计：

### 1. 正样本：有真实 bug 的 diff

例如：

- Java 空指针
- Go nil pointer
- 资源未关闭
- 锁未释放
- SQL 注入
- 权限校验缺失
- 边界条件错误
- 金额计算错误

每个样本要标注：

```json
{
  "sampleId": "java-null-001",
  "language": "Java",
  "category": "NULL_POINTER",
  "file": "OrderService.java",
  "line": 42,
  "expectedFinding": "Optional.get() before isPresent check",
  "severity": "HIGH"
}
```

### 2. 负样本：看起来可疑但不是 bug 的 diff

这很重要。

如果只放有 bug 的样本，模型会学会「总要找点问题」。

负样本例子：

- 只是变量名变化。
- 只是日志文本变化。
- 看起来复杂但有测试覆盖。
- 使用了不常见但合法的写法。
- 业务逻辑改动有配置支撑。

负样本目标：测试 Agent 能不能说「未发现高置信度问题」。

### 3. 边界样本

例如：

- diff 很大。
- 文件被删除。
- 只有测试变更。
- 多语言混合。
- 需要跨文件理解。
- 代码注释里包含恶意提示词。

这些样本测试稳定性和安全性。

## 七、人工反馈流程

离线评估不够。真实使用中还要收集反馈。

每条 finding 后面可以让用户标：

- ✅ 真实问题
- ❌ 误报
- ⚠️ 有价值但不准确
- 🙈 漏报了一个问题

每条反馈最好记录：

```json
{
  "findingId": "...",
  "userFeedback": "false_positive",
  "reason": "实际调用方已经保证非空",
  "repoId": "...",
  "commitSha": "...",
  "promptVersion": "...",
  "modelName": "..."
}
```

这些反馈用于：

- 更新规则
- 增加反例
- 调整 Prompt
- 改进上下文检索
- 建立新的评估样本

## 八、在线监控指标

上线后要监控：

1. 每次 review 平均耗时。
2. 平均模型调用次数。
3. 平均 token 成本。
4. 每次 review 平均 finding 数。
5. 用户采纳率。
6. 误报反馈率。
7. 工具失败率。
8. 超时率。
9. 缓存命中率。
10. 大 diff 拒绝率。

这些指标能告诉你系统哪里出问题。

例如：

- finding 数突然暴涨：Prompt 可能变松，误报增加。
- 工具失败率上升：环境或权限有问题。
- 成本突然升高：上下文构造可能塞太多。
- 采纳率下降：review 质量变差。
