## 正文内容

到现在，你已经知道怎么做一个最小 Agent。

但最小可运行，不等于可上线。

真实 AI 应用会遇到这些问题：

- 模型调用超时。
- 模型输出不是合法 JSON。
- 工具调用失败。
- 同一个工具被重复调用。
- 用户连续提交大 diff，成本暴涨。
- 上下文太长，模型漏看关键代码。
- 静态分析工具卡住。
- Agent 一直循环，不知道停。

所以，本篇讲 AI 工程稳定性的 5 个基础能力：

> **错误处理 → 重试 → 限流 → 缓存 → 成本控制**

我们用「代码 review Agent」作为主例子。

## 一、错误处理：先给失败分类

错误处理第一步，不是写 `try-catch`，而是给失败分类。

AI 应用常见失败至少有 6 类。

### 1. 输入错误

用户输入或系统输入不满足要求。

代码 review Agent 里可能是：

- diff 为空。
- diff 太大。
- 文件类型不支持。
- 用户没有仓库权限。
- 变更文件已被删除，无法读取上下文。

处理方式：尽早拒绝或要求补充信息，不要浪费模型调用。

### 2. 模型调用错误

模型 API 调用失败。

可能是：

- 超时。
- 网络失败。
- 服务端错误。
- 请求过大。
- 速率限制。

处理方式：根据错误类型决定是否重试、降级或失败。

### 3. 模型输出错误

模型返回了内容，但系统无法使用。

可能是：

- JSON 不合法。
- 字段缺失。
- 枚举值不在允许范围。
- 行号不存在。
- 问题描述没有证据。

代码 review Agent 里，模型不能只说：

```text
这里可能有问题。
```

更应该输出结构：

```json
{
  "file": "src/main/java/OrderService.java",
  "line": 42,
  "severity": "HIGH",
  "category": "NULL_POINTER",
  "evidence": "orderRepository.findById(id) 可能返回 empty，但后续直接 get()",
  "suggestion": "使用 orElseThrow 或显式处理 empty"
}
```

然后系统校验：文件是否存在，行号是否在 diff 附近，严重级别是否合法。
??? 这个只是 agent 内部输出结构? 最终输出结构我理解应该是个 html 格式?

### 4. 工具执行错误

工具调用失败。

代码 review Agent 里可能是：

- Git 命令失败。
- 静态分析超时。
- 测试失败。
- 文件读取失败。
- 编译环境缺依赖。

处理方式：记录工具错误，并决定是否继续做部分 review。

### 5. 业务规则错误

结果违反业务规则。

例如你的规则是：

> 只输出高置信度 bug，不输出风格建议。

但模型输出：

```text
变量名可以更优雅。
```

这不是工具错误，也不是模型调用错误，而是业务规则违背。系统应该过滤掉。

### 6. 安全错误

涉及权限、隐私、敏感操作。

代码 review Agent 里可能是：

- 模型要求读取无关目录。
- 模型尝试访问密钥文件。
- 用户提交的代码里包含提示注入文本。
- 工具参数越权。

处理方式：拒绝、截断、脱敏、告警。

## 二、Java 错误模型：不要只抛异常

只靠异常，调用方很难判断下一步。

更稳的方式是定义错误类型。

```java
public enum AiErrorType {
    INVALID_INPUT,
    MODEL_TIMEOUT,
    MODEL_RATE_LIMITED,
    MODEL_BAD_OUTPUT,
    TOOL_FAILED,
    PERMISSION_DENIED,
    COST_LIMIT_EXCEEDED,
    UNKNOWN
}

public record AiError(
    AiErrorType type,
    String message,
    boolean retryable
) {}

public record AiResult<T>(
    T value,
    AiError error
) {
    public boolean success() {
        return error == null;
    }
}
```

这样调用方能判断：

- 是不是可重试？
- 要不要降级？
- 要不要返回用户？
- 要不要记录为可修复失败样本？

## 三、重试：只重试值得重试的失败

重试不是「失败就再来一次」。乱重试会放大成本、重复调用工具、制造更多问题。

### 适合重试的错误

- 网络抖动。
- 模型调用超时。
- 临时服务端错误。
- 速率限制后等待再试。
- 工具短暂不可用。

### 不适合重试的错误

- 输入无效。
- 权限不足。
- 请求过大。
- Prompt 设计错误导致稳定输出坏 JSON。
- 工具参数格式错误。
- 用户仓库不存在。

### 代码 review Agent 例子

如果模型调用超时，可以重试一次。

如果用户无权读取仓库，重试 100 次也没用。

如果模型输出 JSON 坏了，可以做一次「修复输出格式」的重试，但不能无限修。

## 四、重试要有退避和上限

重试要有 3 个控制：

1. 最大次数。
2. 退避等待。
3. 总超时。

伪代码：

```java
public <T> AiResult<T> retry(String operationName, Supplier<AiResult<T>> operation) {
    int maxAttempts = 3;

    for (int attempt = 1; attempt <= maxAttempts; attempt++) {
        AiResult<T> result = operation.get();
        if (result.success()) {
            return result;
        }

        if (!result.error().retryable()) {
            return result;
        }

        if (attempt == maxAttempts) {
            return result;
        }

        sleep(backoffMillis(attempt));
    }

    return new AiResult<>(null, new AiError(AiErrorType.UNKNOWN, "retry failed", false));
}

private long backoffMillis(int attempt) {
    return 200L * attempt * attempt;
}
```

重点不是这段代码，而是原则：**重试必须有边界**。

## 五、工具调用要区分幂等和非幂等

幂等意思是：同一个操作执行多次，结果不会造成额外副作用。

### 幂等工具

代码 review Agent 中常见幂等工具：

- 读取 diff。
- 读取文件。
- 搜索代码。
- 运行只读静态分析。

这些工具失败后，通常可以重试。

### 非幂等工具

可能有副作用的工具：

- 自动提交评论。
- 自动创建 issue。
- 自动修改代码。
- 自动推送 commit。

这些工具不能随便重试。否则可能重复评论、重复创建 issue、重复修改代码。

工程规则：

> **只读工具可以有限重试；写操作必须幂等键、确认机制或去重机制。**

例如给每条 review 评论生成稳定 ID：

```java
public record ReviewFinding(
    String findingId,
    String file,
    int line,
    String category,
    String message
) {}
```

`findingId` 可以由 `file + line + category + message hash` 生成。再次提交评论前，先检查是否已经提交过。

## 六、限流：保护系统和预算

限流回答一个问题：**单位时间内允许多少请求或调用？**

AI 应用必须限流，因为模型调用贵，工具调用也可能压垮系统。

代码 review Agent 至少要限 4 层。

### 1. 用户级限流

防止单个用户连续提交大量 review。

例如：每个用户每小时最多 20 次 review。

### 2. 仓库级限流

防止一个大仓库触发大量文件读取、测试和静态分析。

例如：单个仓库同时最多 2 个 review 任务。

### 3. 模型调用限流

限制模型调用次数和并发。

例如：每个 review 最多 20 次模型调用。

### 4. 工具调用限流

限制读文件、搜索、测试等工具。

例如：单个 review 最多读取 200 个文件片段，最多运行 3 组测试。

## 七、缓存：避免重复花钱和重复工作

缓存回答一个问题：**同样输入，能不能复用之前结果？**

代码 review Agent 很适合缓存。

### 1. 文件内容缓存

同一个 commit 下，同一个文件内容不会变。可以缓存文件读取结果。

缓存 key：

```text
repoId + commitSha + filePath
```

### 2. 静态分析结果缓存

同一个 commit、同一套规则，静态分析结果可以复用。

缓存 key：

```text
repoId + commitSha + analyzerVersion + rulesHash
```

### 3. Prompt / 模型结果缓存

同一段 diff、同一版 Prompt、同一模型配置，模型 review 结果可能可以复用。

缓存 key：

```text
diffHash + promptVersion + modelName + modelOptionsHash
```

注意：如果模型有随机性，缓存要更谨慎。工程上可以用低 temperature 和结构化输出，提高可复用性。

### 4. 规则缓存

Review 规则、项目规范、忽略列表也可以缓存。

缓存 key：

```text
repoId + rulesVersion
```

---

## 八、缓存不能乱用

缓存有风险。

### 1. 权限风险

缓存结果不能跨用户乱用。

例如用户 A 有权限看某文件，用户 B 没权限。即使缓存里有结果，也不能给 B。

所以缓存 key 或读取缓存前必须考虑权限。

### 2. 过期风险

代码变了，缓存必须失效。

用 `commitSha` 比用文件路径更稳。

### 3. 规则变化风险

Review 规则变了，旧结果可能不适用。

所以缓存 key 要包含 `rulesHash` 或 `promptVersion`。

### 4. 模型变化风险

模型或参数变了，输出可能变。

所以缓存 key 要包含模型名和关键参数。

## 九、成本控制：先控制输入，再控制调用次数

AI 成本常来自 4 个地方：

1. 输入 token。
2. 输出 token。
3. 模型调用次数。
4. 工具 / 计算资源成本。

代码 review Agent 成本尤其容易失控，因为代码上下文很大。

### 1. 控制输入 token

不要把整个仓库塞给模型。

更好的策略：

- 先只看 diff。
- 再按需要读取相关上下文。
- 只读取调用链关键片段。
- 超大文件只摘取相关函数。
- 配置文件按需读取。

### 2. 控制输出 token

要求模型只输出结构化 finding，不要长篇解释。

例如：

```json
{
  "findings": [
    {
      "file": "...",
      "line": 42,
      "severity": "HIGH",
      "category": "NULL_POINTER",
      "message": "...",
      "suggestion": "..."
    }
  ]
}
```

### 3. 控制调用次数

不要每个文件都单独调用模型。

可以分层：

1. 先用规则和静态分析筛选风险点。
2. 再对高风险 diff 调用模型。
3. 最后只对候选 findings 做二次验证。

### 4. 分级模型策略

不同任务用不同模型能力。

- 简单分类：低成本模型。
- 结构化抽取：低温、稳定模型。
- 复杂跨文件推理：更强模型。
- 最终报告润色：可用普通模型。

不要所有步骤都用最贵模型。

## 十、代码 review Agent 的稳定链路

把本篇内容串起来，一个更稳的代码 review Agent 可以这样跑：

```text
用户提交 review 请求
  ↓
输入校验：仓库权限、diff 是否为空、文件类型是否支持、diff 大小是否超限
  ↓
读取 diff：缓存文件内容和变更块
  ↓
静态分析：可重试，可缓存
  ↓
构造上下文：只放 diff、关键上下文、规则和输出 schema
  ↓
模型审查：低温、结构化输出、有限重试
  ↓
输出解析：JSON 解析、字段校验、行号校验、严重级别校验
  ↓
二次验证：检查 finding 是否有证据，是否属于高置信度问题
  ↓
结果过滤：去掉风格建议、低置信度建议、重复 finding
  ↓
成本检查：记录 token、调用次数、耗时、工具次数
  ↓
结果展示：按严重级别输出 review 报告
```

这就是从 Demo 到工程的分界线。

## 十一、最小稳定性清单

做任何 AI 应用，至少问这 10 个问题：

1. 输入无效时怎么办？
2. 模型超时时怎么办？
3. 模型输出格式错时怎么办？
4. 工具失败时怎么办？
5. 哪些错误可以重试？哪些不能？
6. 每次请求最多调用模型几次？
7. 每次请求最多调用工具几次？
8. 哪些结果可以缓存？缓存 key 是什么？
9. 缓存是否考虑权限、版本和过期？
10. 成本超限时如何降级或停止？

如果这些问题没答案，应用就还不稳定。
